# Changelog

All notable changes to the Quadrate programming language are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **`sort::by`, `sort::is_sorted_by` and `sort::lower_bound_by`**: sorting, checking and binary search ordered by a caller-supplied comparator, using the same negative/zero/positive convention as C's `qsort`. The module's six entry points each fixed both the element type and the direction because a function could not take a comparator; sorting by a key, by several fields, or descending are all just comparators now.
- **Function-pointer tests**: `fntype/fn_field_dispatch` (dispatch through a struct field, plus fields returning several values, none, and a struct that is chained), `fntype/fn_param_call` (a declared parameter, through a type alias and passed on to another function), and the rejections `compile_errors/fn_field_signature_mismatch` and `fn_call_result_unconsumed`.
- **Generics tests**: `generics/generic_array_param` (`[]T` bound to i64/str/f64 element types), `generics/generic_fn_param` (`fn(T -- T)` with a named fn, a differently-typed one, and a lambda), `generics/generic_struct_return` (fields of a returned `Box<T>`), `modules/module_generic_arrays` (the same through module-qualified calls), and the rejections `compile_errors/generic_binding_conflict`, `generic_fn_param_mismatch`, `modules/module_array_param_mismatch`.
- **`switch` arm stack-effect rule** (spec §6.4.1). Every arm that reaches the merge point must leave the stack at the same depth, as `if`/`else` arms already had to; a `switch` with no `_` arm must additionally leave the stack as it found it, since no arm may run. `c switch { 1 { 10 }  2 { 20 30 }  _ { 0 } }` in a `( -- r:i64)` function used to compile and return whichever value happened to be on top. Diverging arms are exempt, and after a bare fallible call the `Ok` arm is seeded from the call's results and every other arm from the pre-call stack.
- **`qd_stack_truncate(ctx, target)`** in `libqdrt`, and a matching freestanding stub. Emitted on the failure exit of every fallible function: see the runtime entry under *Changed*.
- Regression tests pinning the checks that were switched off (below) with a call in the body — `compile_errors/arity_check_after_call`, `arity_check_after_module_call`, `if_arms_unbalanced_after_call`, `defer_effect_after_call` — plus `failure_arm_drop`, `fallible_if_result_unconsumed`, `switch_arms_unbalanced`, `switch_no_default_changes_stack`, and positive tests for balanced-arm retyping, fallible methods before `if`, fallible `if` without `else`, `Ok` versus a literal `1` arm, `panic` followed by dead code, and module functions with no outputs and control flow in the body.

- **fish completions** (`completions/quad.fish`), covering all ten tools with per-option descriptions, subcommand dispatch for `quad` and `quadpm`, and passthrough so `quad lint --<TAB>` offers what `quadlint` accepts. File operands are filtered to `.qd` (and `--css` to `.css`) rather than merely ranked: `__fish_complete_suffix` sorts matches first but still returns every file, so it would have offered `CHANGELOG.md` for `quadfmt`. fish autoloads by command name as bash-completion does, so `make install` links `<tool>.fish` for each tool alongside `vendor_completions.d/quad.fish`; the file is staged into `dist/` and shipped in the release tarball. `cli_surface_test` checks the tool list and the option lists against each tool's `--help`, and runs `fish -n` where fish is available.
- **zsh completions** (`completions/_quad`), covering all ten tools with per-option descriptions, `.qd`-filtered file arguments, and subcommand dispatch for `quad` and `quadpm` — including passthrough, so `quad lint --no-<TAB>` offers what `quadlint` accepts. One file serves every tool: its `#compdef` line names all ten and zsh indexes it by them, so unlike bash-completion it needs no per-command links. Installed to `$DATADIR/zsh/site-functions/_quad`, staged into `dist/` and shipped in the release tarball. `cli_surface_test` checks the `#compdef` line, the `$service` dispatch and the option lists against each tool's `--help`, and syntax-checks the file with `zsh -n` where zsh is available.
- **`quaddoc` reports files it could not parse**, as `file:line:column: warning: ...`, the located form `quadc` and `quadlint` use, and carries on documenting what did parse. A file the parser chokes on used to be published silently with whatever the text scanner happened to recognise. `-q` silences it.
- **`qdcli::Help`** (`lib/cli/src/help.cc`): a shared renderer for the tools' `--help` pages. Each tool describes its own options and examples; the title line, `Usage:` block, section headings and column alignment are computed in one place. The ten pages had been hand-written `std::cout` sequences with five different description columns between them.
- **`tests/run_cli_surface_test.sh`** (suite `tools`, test `cli_surface_test`): 277 checks pinning what all ten tools share — the shape of `--help`, the format of `--version`, how an unrecognised option is reported, and that the bash completions still list every option each tool documents. Run it with `./tests/run_all.sh --suite tools`.
- **`completions/quad.bash` rewritten** against the tools' actual flags, and covered by `cli_surface_test`, which now fails if an option in any tool's `--help` is not completable. It had drifted a long way: no `--no-color` anywhere, no `quadmcp` at all (despite its own header claiming it), no `pm` or `mcp` under `quad`, no `remove`/`outdated` for `quadpm`, and `quadlint` was missing ten of its flags including `--json`.
- **Long forms for `quadc`'s short options**: `--output`, `--debug`, `--stack-size`, `--include` and `--module` alongside `-o`, `-g`, `-s`, `-I` and `-l`, and `--output` for `quaddoc`'s `-o`. The short spellings are unchanged; every option now has both, as the other tools' already did.
- **`--no-color` on `quad` and `quadmcp`**, the last two tools that rejected it. `quad` consumes it and exports `NO_COLOR` to the tool it runs, so `quad --no-color lint src/` reaches `quadlint`.
- **`BaseOptions::optionError`**: lets a tool's option handler report what was actually wrong with a flag instead of `parseArgs` falling back to "unknown option", which blamed the flag rather than its missing value.
- **`SemanticValidator::finalStackTypes()`, `finalStackStructTypes()` and `finalStackFunction()`**: what the most recently type-checked function body leaves on the stack, including the struct type of each pointer. A REPL compiling one line at a time needs this to re-declare the previous line's end state as the next line's signature.
- **`quadrepl` `:doc <name>`**: shows a name's stack effect — builtins and keywords from the compiler's own reference table, standard library functions from their declaration in the installed `.qd` sources, and functions defined earlier in the session. With no exact match it lists every name containing the text, so `:doc trim` finds `strings::trim_left` without knowing the name.
- **`quadrepl` command aliases**: `:quit` and `:exit` alongside `exit`/`quit`/`:q`, and `:save`/`:load` alongside `.save`/`.load`.

### Changed

- **`hof` is generic.** All seventeen combinators were fixed to `fn(i64 -- i64)` because a generic function-pointer parameter could not be satisfied; they now carry type parameters, so `apply`, `map`, `fold`, `filter`, `any`, `all` and `find` work over floats, strings and structs. `map` is `map<T, U>`, changing the element type — `["a" "bbb"] &length_of hof::map` yields `[1 3]`. The seventeen existing i64 tests pass unchanged.
- **Arrays decide their element type on first use.** An empty `[]` literal was created as an *int* array, so `[] "x" append` failed at run time with a type mismatch, and a generic `map<T, U>` could not build its result. An array now starts with no element type (`QD_ARRAY_TYPE_ANY`) and adopts the type of the first value appended — or written with `set`, which is how `make<T>` inside a generic function behaves, since generics are erased rather than monomorphised and `make<T>` cannot know T at run time. Reading a slot of an array that never received a value gives the integer zero, which is what the zeroed slot holds. `qd_makea` is the new runtime entry point for that case; `make<i64>`, `make<f64>`, `make<str>` and `make<SomeStruct>` are unchanged.
- **The function-level output check compares pointer types structurally**, with the function's own type parameters as wildcards — inside `fn map<T, U>( … -- r:[]U)` the result is built from an empty literal, which is `[]any`, and U is unbound in the body. It was a string equality over array types only, so it rejected that and skipped struct results entirely; a function declaring `-- p:A` while returning a `B` now reports it.

- **A function pointer can be called through a struct field or a declared parameter.** Nothing converted a `fn(...)` type *string* back into a signature — `mPendingFnSignature`, which `call` consults, was set only by `&f`, a lambda, or a local bound directly from one. Everywhere else `call` took its "we don't know what the called function will do" branch: it popped the pointer and pushed nothing. So `s <<area call print` reported a stack underflow, and a fn-typed parameter was no better; the cases that appeared to work did so only because a leftover argument stood in for the missing result. `parseFnTypeString` is the inverse of `buildFnTypeString`, and `call` now falls back to it using the type the value carries. Dynamic dispatch through a struct field — a vtable — works, including fields whose functions return several values, no values, or a struct that is then chained into a field read.
- **`call` no longer switches off the function-level checks.** Its branch fell out of the `if`/`else if` chain in `typeCheckInstructionInternal` into the trailing `mHasUnpredictableStack = true`, which is a plain statement rather than an `else`, so every function containing a `call` lost its arity, `if`-arm and `defer` checks — the same shape as the `IDENTIFIER` bug fixed above, and the reason `fn run(f:fn( -- f64) -- ) { f call }` compiled while leaving a value behind. The flag is now set only when the callee's effect is genuinely unknown, which is still the case for an untyped `ptr`.
- **A function pointer is checked against the field it initialises.** The struct-construction field check had no case for `&f` or a lambda, so their type was `UNKNOWN` and any function satisfied any `fn`-typed field: `H { f = &shout }` with `f:fn(i64 -- i64)` was accepted. The comparison it does reach was a raw string compare, which would have rejected the `fn(-- f64)` spelling `buildFnTypeString` emits against a declared `fn( -- f64)`; it now unifies structurally, as call arguments do.
- **`buildFnTypeString` renders declared type names**, so a function returning a struct is `fn( -- Point)` rather than `fn( -- ptr)` — the coarse stack types cannot tell those apart, and a field declared `fn( -- Point)` would not have matched. `any` and a bare `ptr` mean "not known well enough to check" only where a comparison starts: nested they are real element types, so an empty `[]` literal (`[]any`) still fails against a declared `[]i64`. A field initializer is strict from the start, since it is a definite assignment rather than a value of unknown provenance — `old_make -> x  Container { data = x }` with `x:ptr` stays an error.

- **Generic type parameters unify structurally, so `[]T` and `fn(T -- T)` work.** Parameter and result types were compared as literal strings by `structTypesMatch`, so `fn count<T>(a:[]T -- n:i64)` rejected `[1 2 3]` with *"expects type '[]T' but got '[]i64'"* and `fn apply<T>(x:T f:fn(T -- T) -- r:T)` rejected `&dbl`. A call site now unifies each declared type against the argument's, recursing through `[]X`, `fn(A -- B)` and `Name<X>` and binding the type parameters as it goes (`unifyTypeName` in `semantic_validator_internal.h`), then substitutes the bindings into the results. `FunctionSignature` carries the declared type names and the function's type parameters, which it previously dropped; the coarse `consumes`/`produces` types cannot express this, since `[]T` and `[]i64` are both `PTR`. This is why `sort` has six monomorphic entry points and `hof` is hardcoded to `fn(i64 -- i64)` — those APIs can now be generic, and `type` aliases for fn-pointer types become usable. An `any` on the argument side means "unknown" only at the top level: nested, it is a real element type, so an empty `[]` literal (typed `[]any`) still fails against a declared `[]i64` while binding a `[]T` freely.
- **A type parameter used twice must bind to one type.** `fn same<T>(a:T b:T -- r:T)` accepted `1 "s"` — there was no binding environment at all, only a "first TYPEVAR wins" heuristic that also mistyped the results of `fn pair<A, B>`. Results are now substituted from the real bindings, so `[1 2 3] first 10 +` type-checks as `i64` and `"a" wrap <<value` as `str`.
- **Module-qualified calls check their argument types.** The struct/array/fn-pointer parameter check existed only in the unqualified-identifier path, so `mod::f` accepted anything of the right coarse type. Both paths now share `bindCallTypeParams` and `pushCallResults`; an unqualified struct name that names an imported module's struct is canonicalised (`Flag` ↔ `flag::Flag`) before comparison, which is how the check passes on code that mixes the two spellings.
- **An instantiated generic struct keeps its type arguments.** `Box<i64> { value = 5 }` pushed the type `Box`, so `<<value` reported the field as the declaration's `T`. The struct-type stack now carries `Box<i64>`, `lookupStructFieldTypes` strips the arguments, and the new `resolveFieldType` maps a field declared as a type parameter to the corresponding argument — so `5 wrap <<value 1 +` type-checks and `>>value` still accepts any type when the instantiation leaves the parameter open.

- **`ident <<field` is no longer folded by the parser.** When the token before `<<` was a plain identifier, the parser deleted that node and stored its name inside the field-access node, and every consumer then had to redo name resolution to learn whether it had been a variable, a function or a struct type. Codegen got all three right; the validator had no function branch and fell through to "search every struct for a field with that name", so a call with arguments before `<<` never consumed them — `7 mk1 <<a` reported one phantom value, `7 8 mk2 <<b` two — and `5 wrap <<value print nl drop` compiled and then underflowed at runtime. The identifier now stays its own node and `<<field` always reads the struct on top of the stack, exactly as `>>field` always did. `AstNodeFieldAccess` and `AstNodeFieldSet` carry only the field name; the JSON AST dump no longer has a `varName` key. Three places that had silently depended on the folded name were made stack-based with it: the validator's construction-time field-initializer evaluator (which had no `<<` case at all, so `Vec2 { x = a <<x ... }` reported the *struct* as the field value once the operand was a real node), the isolated signature analysis (which pushed the field without popping the operand), and closure codegen, which registered captured variables without their struct type. A zero-argument call before `<<` on a field name shared by several structs also resolves now — codegen used to hit its ambiguity fallback because the folded path never consulted the call's return type. The `error <<code`/`error <<message` special case that rode on the fold is gone; its one use, a program embedded in `tests/run_tools_test.sh`, now reads the code with `err` as the documentation says to. `<<` and `>>` diagnostics name the struct and suggest fields; `>>field` additionally checks the value's type against the field's.
- **The declared-effect, `if`-arm and `defer` checks now run in functions that call other functions.** `mHasUnpredictableStack = true` in the validator sat *after* the block that applies a resolved call's signature, so it executed for every `IDENTIFIER` and `SCOPED_IDENTIFIER` call, resolved or not — the comment beside it described the not-found case the code never tested for. The three checks gated on that flag (`declares N output(s) but body leaves M`, the `if`/`else` depth rule, and `defer` must have zero net effect) were therefore dead in any function that called anything, since the check was introduced in `3267700f`. `fn bad( -- r:i64) { helper 99 }` compiled clean. All four regression tests pinning the arity error had literal-only bodies, so the suite could not see it. The flag now moves into the not-found branch of both copies. **This is breaking for code that was wrong**: the sweep over the whole standard library and every example found three functions (below), and the test suite found nine tests encoding pre-spec conventions, all rewritten.
- **A failure arm is modelled from the pre-call stack, and a `drop` in it is a compile error.** The validator seeded the `else` arm of an `if` after a fallible call from the *success* stack ("both branches receive result values from fallible calls"). At runtime the call produced nothing, so `drop  // drop unused string` in `flag::int`/`flag::float`'s failure arms popped the *caller's* value from the shared stack before panicking — verified with a sentinel — and `examples/errors/errors.qd` taught the same pattern. The arm now starts from the stack as it was before the call, so the `drop` underflows at compile time, which is what spec §10.3 has said all along. The `Ok` arm of a `switch` is seeded from the results and every other arm from the pre-call stack; a literal `1` arm is an error-code arm, not `Ok`.
- **The success arm of a fallible `if` must leave the same depth as the failure arm.** Previously any depth mismatch after a fallible call was suppressed wholesale. With the failure arm modelled correctly the general rule applies, so `divide if { "ok" print nl } else { ... }` — which leaves the result on the success path only — is rejected with a hint to consume or drop it. A fallible `if` with no `else` likewise merges to the pre-call stack and requires the success arm to leave that depth (`try_all` in the error-handling docs, which drops the result in each arm, is the shape that now type-checks *because* of this: it used to be reported as leaving four values). The spec's own §10.6 example left the result on two "unreachable" success arms and has been corrected.
- **A fallible function's failure exit truncates the stack to what the caller expects** — the depth at entry minus the declared inputs and receiver. `panic` branched to the return block and left the stack as it was, so a callee with unnamed parameters that panicked before consuming them (`fn g(i64 -- i64)! { dup 0 < if { "neg" 1 panic } ... }`) left its input for the caller's failure arm, and the old "push an error value, then panic" convention in four tests relied on exactly that. Named-parameter callees already behaved correctly because binding pops the inputs at entry. The truncation makes the validator's model exact for every callee body, releases any strings it drops, and leaves pointers alone for the same reason `drop` does.
- **Balanced `if`/`else` arms now yield the arms' types, not the pre-`if` types.** The merge handled effects `> 0` and `< 0` but had no branch for `== 0`, so arms that transformed a value in place (`-> s  s parse_float` in one arm, a diverging `panic` in the other) reported the *input's* type as the function's output: `flag::float ... expects float but got string`.
- **A block diverges when any top-level statement in it is `panic`, `return`, `break` or `continue`** — not only when the last one is. `"msg" 1 panic  0.0` was not recognised as diverging, which is why `flag.qd` carried dummy pushes after its panics. `break` and `continue`, which spec §6.1.1 always listed, were not checked at all.
- **A fallible *method* call before an `if`/`switch` is recognised as one.** The check looked the callee up by bare name; methods are keyed by their mangled name, so `f name string if { ... }` inside `flag.qd` was treated as an ordinary `if`. Both `if` and `switch` now resolve the preceding call through one helper that knows about methods and module qualification.
- **Module functions with no declared outputs produce nothing.** `analyzeModuleFunctionSignatures` fell back to the isolated body analysis' residual stack when a function declared no outputs, and for any body with a loop, `switch`, `if` or an unmodelled call that residual was the function's own *inputs*. `bytes::fill(value buf offset count -- )` was registered as producing four values, `bytes::copy` five, and any `( -- )` module function with a loop leaked its inputs into the caller's model. `collect.cc` had already rejected this idea ("body analysis is unreliable for control flow"); the module builder now agrees, and its scalar type mapping goes through `stringToStackValueType`, so sized-integer parameters in module functions are checked as integers instead of accepted as `any`.
- **Generic type parameters are skipped in method-call argument checks**, as they already were in function-call checks. `v 10 push!` on a `Vec<i64>` reported *"Parameter 1 expects typevar, but got int"* once the signature carried the parameter's real type.
- **Diagnostics** for the `if` rule report the arms' resulting depths (`then: 2 value(s), else: 1 value(s)`) rather than effects measured from different bases, and carry a hint after a fallible call.

- **`quaddoc` reads declarations from the compiler's AST.** It was the only tool that re-implemented parsing, matching `pub fn`, `struct`, `const` and struct fields with 28 hand-written regular expressions, and it silently dropped every form those patterns had not anticipated. Structure -- which declarations exist, their names, parameters, receivers, generics and visibility -- now comes from `Qd::Ast`, the same parser `quadc`, `quadlint`, `quadfmt`, `quaduses` and `quadlsp` use. 12 regular expressions remain and none of them parse Quadrate: ten match the `@param`/`@return`/`@error`/`@example`/`@field` tag language, which lives inside comments the lexer discards and so has no AST, and two expand `use foo.qd` file includes before parsing.
- **Parameter tables describe the parameters the function actually has.** Names, types and order come from the signature; `@param` and `@return` supply only the prose, matched by name and falling back to position. Where the two disagreed the documentation used to publish the tag: `bits::set_bits` was documented as taking `target value start_bit num_bits` when it takes `tgt val sb nb`, and every `rand` receiver was typed `ptr` where the declaration says `Rng`. A method's receiver is now the first row of its parameter table rather than being dropped.
- **Every tool's `--help` follows one layout**: `<tool> - <summary>`, a description paragraph, `Usage:`, an `Options:` block opening with `-h`/`-v`/`--no-color` in that order and worded identically, any tool-specific sections, then `Examples:`. `quadlsp`, `quadmcp` and `quadrepl` had no examples; `quadfmt` listed the stdin note in the middle of its options; `quaddoc` and `quadmcp` folded their description into the title line. `quad`'s page no longer colours itself, matching the other nine, and its command list is generated from the dispatch table it already had rather than retyped beside it.
- **Compiler diagnostics drop the `quadc: ` prefix** when they carry a source location: `main.qd:7:2: error: ...` rather than `quadc: main.qd:7:2: error: ...`. This is the gcc/clang form every editor's error parser expects, it is what `quadlint` already emitted, and the prefix is wrong on its face in a reporter that `quadlsp` and `quadrepl` link too — both were announcing themselves as `quadc`. `quadc`'s own failures (`quadc: no input files`) keep the prefix, since nothing else identifies them. The error-limit note no longer names a tool either. 28 `.err` test patterns updated.
- **`quadpm`'s diagnostics match the other tools.** It printed a capitalised, red `Error: `/`Warning: ` prefix where every other tool writes `<tool>: <message>` in lower case on stderr; 23 sites now go through `pmError`/`pmWarn`/`pmUsageError`. Scripts grepping for the old `Error: ` prefix need updating — the text after `quadpm: ` is otherwise unchanged in meaning.
- **`quadmcp --version`** reports `quadmcp <version> (<commit>, built <date>)` like its siblings instead of a bare `quadmcp 0.5.0`. It is compiled from `.qd` and cannot include the generated `version.h`, so the Makefile emits the same string as a Quadrate `const` from the same two `git describe` calls meson and `lib/version` use.
- **`quadlint` reports a bad option value once.** `--max-nesting` with no argument printed `quadlint: --max-nesting requires an argument` followed by `quadlint: unknown option: --max-nesting` — two lines contradicting each other. It now prints one, in the `option '--max-nesting' requires an argument` wording the other tools use.
- **`quadc` with no arguments** reports `quadc: no input files` on stderr and exits 1, rather than printing its whole help page to stdout with a failure status. The tools that take paths all behave this way now; `quad` and `quadpm` dispatch commands, so a bare invocation of those still shows help and exits 0.
- **`quadrepl` keeps values on the stack.** A line that left values behind did not compile — `repl_main` declared no outputs — so the REPL retried it with a synthetic `print nl drop...` until an arity fit, printing the values and then dropping them. Every prompt therefore showed an empty stack, which is most of what a stack language REPL is for. It now asks the validator how many values the body leaves and declares that many `any` outputs, so `5 3` gives `[5 3]>` and `add` gives `[8]>`. Values are no longer echoed a line at a time; with stdin on a pipe the final stack is printed at end of input, as `-p` does explicitly.
- **`quadrepl` tab completion reads the standard library from disk.** The hand-maintained table it replaces offered `strings::index`, `strings::substr`, `strings::ltrim` and `strings::rtrim` — the real names are `index_of`, `substring`, `trim_left` and `trim_right` — spelled the math constants `PI`/`E`/`TAU` instead of `Pi`/`E`/`Tau`, and knew nothing of the modules added since it was written.
- **`quadrepl` compiles and runs each line once.** Every line used to be compiled and executed with the whole session replayed in front of it. That made a session quadratic, and it re-ran side effects: one `io::append_file` followed by three more lines wrote four lines to the file. A line is now compiled on its own, taking the state the previous line left — the stack, and the names bound at top level — as its input signature and handing it back as outputs. The arity probe that cost up to eight codegen-and-link cycles per line is gone with it; the count comes from one in-process validation pass.
- **`quadrepl` accepts `struct`, `enum`, `const`, `type` and `var` declarations.** Only `fn` and `use` were recognised, so `struct Point { x:i64 y:i64 }` went into the body of the generated function and came back as `Undefined identifier 'struct'`. Declarations are kept for the rest of the session, as function definitions already were.
- **u8t tokenizer updated to 1.4.0.** The local `u8t-scanner-eof.patch` is dropped — upstream now stops a string token at end-of-input without consuming the terminator, which is what the patch did. Malformed numeric literals (`0x`, `0b` and `1e` with no digits after them) are reported as `Unexpected character` rather than `Invalid integer literal`; the tokenizer classifies them as errors instead of handing the text to the parser. Rejection of exponent notation is unchanged: `1e300` is still an error, `2.2250738585072014e-308` is still a float.

### Fixed

- **`sort::ints`, `sort::ints_desc`, `sort::floats` and `sort::floats_desc` returned unsorted data.** Each partition bounded its left scan by `j` rather than by `hi`. The scan could then stop on an element that still sorted before the pivot, and the pivot swap that follows placed the pivot to the left of it. Every reverse-sorted input of even length 18 or more came back unsorted — silently, since nothing checked the result. Found while writing `sort::by`, which mirrors the same partition. The pivot at `hi` is the scan's sentinel, so bounding by `hi` is both correct and sufficient. New tests sort reverse-sorted input at every length from 2 to 60 for `ints`, `floats` and `by`; a separate stress run over ~1,000 sorts (random values, heavy duplicates, reverse-sorted, all-equal; ascending and descending) reports no failures.

- **`flag::int` and `flag::float` corrupted the caller's stack when the flag was missing.** Their failure arms dropped a value the failed `string` call never produced, eating whatever the caller had on the shared stack, then panicked; the dummy `0`/`0.0` after each `panic` was dead code. Found by the re-enabled checks above.
- **`regex::get_cclass` pushed the integer `0` where the signature promised a `ptr`** on the not-found path; it now pushes `null`. Found by the re-enabled output-type check.
- **`examples/errors/errors.qd`** dropped a non-existent error value in both failure arms and pushed a dummy result before `panic`; it now reads the error with `err` and matches the spec.
- **Documentation examples that left values on the stack or read the wrong one**: `reference/generics.md` (three `identity` calls with nothing consuming them), `learn/8-examples/user-input.md` (`io::readline` returns `line ok`; two examples bound only one value and a third cast the `ok` flag instead of the line), and the §10.6 worked example in the specification (results left on "unreachable" success arms). `docscheck` covers 218 blocks and passes.
- Nine language tests encoded the pre-spec convention of pushing an error value before `panic` and dropping it in the failure arm (`errors/always_success`, `conditional_error`, `error_recovery`, `recovery`, `fallible_protocol_unified`), or declared no outputs for a function that returns one (`modules/advanced_ops`), or relied on the checks being off (`modules/bytes_module`, `enums/module_enum`, `imports/*`). All rewritten to what the spec says; expected outputs are unchanged.

- **`quaddoc` and `quadmcp` had no shell completion in practice.** bash-completion loads a completion file lazily, by the name of the command being completed, so the one file serving all ten tools needs a link under each tool's name. `make install` created seven links from a hand-written list that omitted those two, and the `dist/` staging step created none at all, so an unpacked tarball completed only `quad`. All three rules now derive the list from one `COMPLETION_LINKS` variable, and `make print-completion-links` exposes it so the test suite checks the real list instead of a copy.
- **The `sys` module was missing from the documentation entirely** -- all 17 functions and the module page. `quaddoc`'s pattern required `pub fn`, so `pub inline fn`, which is how every function in `sys` is declared, matched nothing.
- **The `ct` container library was missing its functions** -- `vec`, `deque`, `hashmap`, `queue`, `pair` and `set` published a struct and nothing else, and `ct` itself showed 4 of its 22 functions. A generic declaration such as `pub fn (v:Vec<T>) push<T>(elem:T -- v2:Vec<T>)!` did not match a pattern that expected `(` straight after the name.
- **Signatures with a function-pointer parameter were truncated mid-type.** `hof::map` was published as `fn map(arr:[]i64 f:fn(i64 -- i64)` -- the parameter list was cut at the first `)`, losing the rest of the parameters and the entire return section. 17 signatures were affected.
- **Receiver methods were rendered as syntax that does not exist**: `fn f:Flag destroy()` rather than `fn (f:Flag) destroy()`. 105 signatures were affected; they can now be pasted back into a source file.
- **The cross-reference graph counted words in comments, builtins and field accesses as calls.** It matched identifiers in raw body *text*, so `rand::next` was listed as calling `rand::new` because its body says "Return new state" in a comment, `math::abs` as calling the `Vec2` method `math::neg` because it uses the `neg` builtin, and every `sb` function as calling `sb::len` because of `<<len` field accesses. 36 such edges are gone and no genuine call was lost.
- **`ImportedFunction::line` and `::column` were wrong in any file containing non-ASCII before the declaration.** The import parser passed `u8t_scanner_token_start`, a character index, straight to `fastLineColumn`, which wants a byte offset; every other call site converts first. In `math.qd`, whose doc comments give ranges as `[-π/2, π/2]`, the recorded line drifted further out with each multi-byte character, so 22 of the imported functions lost their documentation once `quaddoc` began looking declarations up by line. This also misplaced compiler diagnostics pointing into import blocks.
- **`tests/quadpm/test_quadpm.sh` blocked for a minute and then failed tests 36 and 37** on any machine with `commit.gpgsign` set globally. One of its seven throwaway git repositories did not disable commit and tag signing the way the other six do, so `git commit` waited on pinentry. The suite now finishes in under a second instead of timing out.
- **`quadmcp` ignored an unrecognised option and started serving anyway**, exiting 0. A mistyped flag therefore looked like a hang to whoever typed it, since the process sat waiting for JSON-RPC on stdin. It now reports the option and exits 1 like every other tool.
- **`quadpm` printed its entire help page to stdout on an unknown command**, burying the one line that said what was wrong. It prints the two-line diagnostic on stderr instead.
- **`echo 'code' | quadc` could not reach the stdin path.** `quadc` short-circuited on `argc == 1` before argument parsing, so the "no files and stdin is piped" branch was unreachable without a flag; `quadc -r` worked and bare `quadc` did not.
- **`quaddoc -o`, `--title` and `--css` with no value** were reported as unknown options rather than as options missing an argument.
- **`use` of any standard library module failed from a build tree.** `qd_build` looked for module archives under `lib/<name>/` and module sources under `lib/qd<name>/qd/<name>/`; both moved to `stdlib/<name>/` in 0.5.0 and these two lookups were not updated. Nothing was linked, and the module failed at `dlopen` with an undefined `usr_<module>_<function>`. This made the whole standard library unusable in `quadrepl` and in any host embedding `libqd`.
- **`quadrepl` rewrote the word `print` inside string literals.** The print-to-`print nl` conversion and its inverse for history matched substrings, so `"hello print world"` evaluated as `"hello print nl world"`. Both now skip string literals and comments.
- **`quadrepl` prompt escape sequences** are wrapped in `RL_PROMPT_START_IGNORE`/`RL_PROMPT_END_IGNORE`, so readline no longer counts the colour codes as visible columns and misplaces the cursor on a wrapped line.
- **`quadrepl` `reset`** left the runtime stack in place while clearing the history behind it.
- **`quadrepl` history file** grew without bound; it is now capped at 5000 entries.
- Stack floats print as `2` and `1.41421` rather than `2.000000`; long strings are elided in the prompt but shown whole by `stack`.
- `qd_clone_context` leaked `error_context` when the `program_name` copy failed.

### Removed

- **`ctx` keyword**: `ctx { ... }` ran its body on a copy of the stack and appended only the body's top value to the parent. Nothing in the corpus used it and the static checker could not model it. There is no drop-in replacement — inlining the body is *not* equivalent, since it consumes the values `ctx` preserved; bind what the body needs with named locals and push the result explicitly. Using it reports the removal.
- **Eight stack shufflers**: `drop2`, `dupd`, `nipd`, `over2`, `overd`, `swap2`, `swapd`, `tuck`. All had zero uses; named parameters and `->` locals cover what they did. Using one reports the removal together with its old stack effect and the equivalent named-local rewrite.
- **Eight C runtime entry points** (`qd_drop2`, `qd_dupd`, `qd_nipd`, `qd_over2`, `qd_overd`, `qd_swap2`, `qd_swapd`, `qd_tuck`) from `<quadrate/rt/runtime.h>` and `libqdrt`. **This is a breaking change for out-of-tree embedders** that called them directly: `libqdrt.so` carries no soversion, so the upgrade is silent and fails at link or load time with an undefined symbol. Replace each call with the equivalent sequence of `qd_stack_push`/`qd_stack_pop`.
- Phantom `error` builtin from the language reference. It was documented with a signature and an example but never existed; the instruction is `err`.

## [0.5.0] - 2026-04-16

### Added

- **`inline` function modifier**: functions declared with `pub inline fn` are inlined at every call site via LLVM's `AlwaysInline` attribute. Works at all optimization levels including `-O0`.
- **`sys` standard library module**: zero-overhead inline wrappers for raw memory access (`sys::st8`/`st16`/`st32`/`st64`, `sys::ld8`/`ld16`/`ld32`/`ld64`), x86 I/O ports (`sys::port_in8`/`port_in16`/`port_in32`, `sys::port_out8`/`port_out16`/`port_out32`), and CPU control (`sys::cli`, `sys::sti`, `sys::hlt`).
- **Freestanding compilation** (`quadc --freestanding`): compile without libc for bare-metal targets. Emits `.o` with a `_start` shim using a static runtime context. Rejects hosted-only builtins and most stdlib modules at compile time.
- **Freestanding runtime** (`lib/rt/src/freestanding.c`): minimal no-libc runtime with static context, halt hooks (x86/ARM/AArch64), and value-stack operations. No heap, no I/O.
- **Freestanding-safe `mem` module**: split into `mem.c` (safe subset: `set_byte`, `get_byte`, `copy`, `zero`, `fill`) and `mem_heap.c` (heap-using: `alloc`, `realloc`, `free`). Freestanding builds link only the safe subset.
- **Raw memory builtins** (`__st8`/`__st16`/`__st32`/`__st64`, `__ld8`/`__ld16`/`__ld32`/`__ld64`): zero-overhead store/load lowering directly to LLVM instructions. Internal — use `sys::st8`/`sys::ld8` instead.
- **x86 I/O port builtins** (`__port_in8`/`__port_in16`/`__port_in32`, `__port_out8`/`__port_out16`/`__port_out32`): lower to inline assembly. x86/x86_64 targets only.
- **CPU control builtins** (`__cli`, `__sti`, `__hlt`): lower to single inline assembly instructions.
- **Type alias declarations** (`type` / `pub type`): compile-time type aliases resolved during semantic validation.
- **String interpolation** (`$"hello {name}"`): desugars to `sb::new`/`sb::append`/`sb::finish`.
- **Boolean literal type**: `true`, `false`, `Ok`, `Err` parsed as boolean literals.
- **Build cache**: content-based incremental compilation using FNV-1a hashing. Skips codegen when output is up-to-date.
- **Test coverage** (`quadc --coverage`): function-entry instrumentation with coverage report after test runs.
- **`quaddoc` cross-references**: call graph with `calls`/`calledBy` arrays and hyperlinks.
- **`quadlint` `//nolint` directive**: per-line or per-rule lint suppression.
- **Typed C embedding API**: `qd_pop_i()`, `qd_pop_f()`, `qd_pop_s()`, `qd_pop_p()`, `qd_error_code()`, `qd_error_message()`, `qd_clear_error()`, `qd_context_stack_size()`.
- **`quadpm` semver-aware update**: resolves constraints from `qd.json`, checks git tags, installs newest compatible version.
- **Improved semver conflict detection**: `rangesHaveCommonVersion()` probing across caret/tilde/explicit ranges.
- **`quadmcp` dynamic module list**: loaded from `docs/api/modules.json` instead of hardcoded.
- **Array syntax in signatures**: `[]i64`, `[]f64`, `[]str`, `[]ptr` types.
- **Function pointer syntax in signatures**: `fn(i64 -- i64)` types in struct fields and parameters.
- **Automated AUR package publishing** via SourceHut CI.
- **`cast<i64>`** now supports pointer-to-integer conversion via `uintptr_t`.
- **Bare-metal x86_64 kernel example** (`examples/kernel/`) with GDT, IDT, PIC remapping, PIT timer interrupts, PS/2 keyboard driver, VGA text output, screen scrolling, backspace, and a `> ` shell prompt. Written in pure Quadrate with assembly bootstrap.
- **New examples**: `csvcut`, `mandelbrot`, `brainfuck`.
- **New test suites**: build cache, freestanding compilation, raw memory, type aliases, string interpolation, inline functions (10 test cases).
- **Documentation**: `inline` keyword in specification, keyword reference, quick reference, and function tutorial. AUR installation instructions.

### Changed

- **`quadfmt` rewritten**: AST-based formatting replacing line-based approach. Formatter now preserves the `inline` keyword.
- **Version numbering** derived from git tags instead of a static `VERSION` file.
- **Deduplicated compiler errors**: parsing errors deduplicated by `line:column:message`.
- **Method call resolution**: uses `userFunctions` map instead of mangled name construction, fixing collisions with builtin instruction names.
- **LSP signature formatting**: empty parameter lists no longer produce spurious ` -- `.
- **Benchmarks modernized**: named parameters and operator syntax replacing stack manipulation.
- **CI**: `quadfmt --check` added to Arch, Alpine, and Debian builds.
- `AlwaysInlinerPass` now runs at all optimization levels (including `-O0`).
- `GlobalDCEPass` skipped in freestanding mode to preserve `pub` functions callable from assembly.
- Target triple and data layout set early in code generation for correct struct layouts on cross-compilation targets.
- Stack struct fields `capacity` and `size` changed from `size_t` to `uint64_t` for consistent layout across 32-bit and 64-bit targets.
- Freestanding mode: `pub` functions get external linkage so they survive DCE and can be called from assembly.
- `make format` now formats both C++/H files (via `clang-format`) and `.qd` stdlib/example files (via `quadfmt -w`).

- i386 data layout patched with `i64:32:64` to match the System V ABI alignment.
