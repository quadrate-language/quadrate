# Changelog

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **`docscheck` checks 1,010 of the documented examples, up from 219.** It compiled only blocks that define `fn main`, so a page showing no whole program was never checked — which is how the front page came to open with an example that does not compile. Three classifiers close most of that gap: a block whose every top-level line opens a declaration is a compilation unit already, so it is compiled with an empty `fn main` appended; `doccheck: continues` compiles a block after the nearest declaration-only block above it in the same file, which is how a tutorial page is written — declare `divide` in one block, use it in the next four; and `doccheck: page-context <preamble>`, a file-level marker, compiles every fragment on a page with that preamble, wrapped in `fn main`, retrying with as many `drop`s as the diagnostic says the fragment left on the stack. The third is what makes a generated stdlib page checkable, where every block is a one-line `@example` from the module's source; it is opt-in per module, declared by a `/// doccheck: page-context` line in the module's own doc comment (which may name extra context, as `strings` does with `use mem` and `thread` with `fn worker() { }`, and values its examples are written against with `doccheck: page-setup`), and every stdlib module is opted in — sixteen that already qualified, plus `crypto`, `regex`, `strings` and `uri` after nine examples were rewritten to stand on their own: three crypto examples were missing their `crypto::` prefix, `regex::release` was shown on a regex that nothing had compiled, `uri::build` was written `u .build` in a notation the language does not have, and four `strings` examples referred to an `entries`/`count` pair from the prose. One of those four documented `strings::from_ptr` as reading an element out of a `strings::split` result, which stopped being true when split started returning `qd_string_t*` — the example now allocates a C string and converts that. One of the broken examples was in `reference.def`, so the compiler's own reference table shipped `fn add(a:i64 b:i64 -- sum:i64) { + }`. The 77 failures this surfaced are all resolved: the broken examples are fixed, and 39 blocks carry a `doccheck: skip <reason>` saying why they cannot be checked (a grammar template, a signature with its body elided, an excerpt shown piece by piece, a pattern sketch, a script for a host that registers the module). The two commonest breakages were one mistake each: a body written stack-direct under a signature with named parameters, and `-> x  // bind parameter` lines left from before parameters bound themselves.

- **Specification §11.2.2, "Ownership"**: who retains and who releases, which §11 never said. It described the mechanism — atomic refcounts, destructors, what a cycle does — without stating the contract every part of an implementation has to share, and three of the defects fixed in this release were that contract implemented differently in different places. The rules: a value on the stack carries a reference of its own; the four places that hold a value (a local, a struct field, an array element, a tagged slot) each own one, take over the reference the stack supplied, release what they replace, and give theirs back when emptied; an instruction that pops a value releases it unless it hands the value on; a value held in several places is freed when the last of them lets go. It follows that memory which will hold references has to be zeroed before first use, since a store reads the old contents in order to release them. None of it shows in what a program prints, so the section says to measure instead, and names the suite that does.

- **`memory` suite case `holders`**: an array of strings, an array of structs, a closure's captured block, a deferred block, a generic struct field and a plain string field, each built and dropped 20,000 times. Those five places were the ones the leak hunt never reached; all five turned out to keep the contract, and now something says so if one stops.

- **`mem::set_any`, `mem::get_any`, `mem::clear_any` and `mem::AnySize`**: a slot that carries a value's type with it — eight bytes of payload and eight of tag, the shape the compiler already gives a generic struct field. `set_i64` and its siblings each know what they are moving; a container written over a type parameter does not, since one body serves every `T` and there is nothing to ask what `T` is. The slot owns what it holds: `set_any` takes over the reference the push handed it, `get_any` takes a fresh one for the stack, and `clear_any` gives the slot's back, so a string or a struct kept in one stays alive exactly as long as the slot does. The region must be zeroed first — a zeroed slot reads as the integer `0` and owns nothing. Hosted only: the freestanding `mem` archive excludes it, as it does `alloc`.

- **`json::parse` — a real JSON parser.** The module could read a value out of a document but had no way to read the document: `get_int(json:str key:str -- value:i64 found:i64)` and its twenty-six siblings each scan the text from the start, so pulling *n* fields out of one document costs *n* scans, and pulling one field out of every element of an array costs a scan per element. Measured on a 71 KB array of 2,000 objects, one `id` per element: **27.0 s through `array_get_object` + `get_int`, against 0.42 s to `parse` and 0.015 s to walk the result** — sixty times faster, and the gap widens with the document.

  `parse` reads the document once into a `Value` tree and reports failure with the byte offset (`json: expected a colon at offset 17`), under the codes `ErrSyntax`, `ErrType`, `ErrIndex`, `ErrKey` and `ErrDepth`. It is RFC 8259 strict where the scanners were lenient: `01`, `.5`, `1.`, `[1,]`, a control character inside a string and a trailing second value are all rejected. `\uXXXX` escapes are decoded, surrogate pairs combined, and a lone surrogate becomes U+FFFD; other UTF-8 passes through byte for byte. An integer literal too wide for `i64` keeps the value a double can hold rather than failing the parse. Nesting is capped by `MaxDepth` (200), since the parser is recursive.

  Reading: `as_int`, `as_float`, `as_str`, `as_bool`, the `is_*` predicates, `len`, `at`, `get`, `has`, and `first`/`next`/`has_next`/`name` for walking children in linear time — `at` walks from the head on every call, the children being a linked list. Building: `new_null`, `new_bool`, `new_int`, `new_float`, `new_string`, `new_array`, `new_object`, `push` and `put`, with `stringify` and `pretty` to write the result back out. `stringify` writes the shortest number that reads back as the same double, so `0.1` stays `0.1` and `1e21` does not become `1e+21` rounded to six digits.

  The scanners stay: for one lookup in one document they allocate nothing and remain the cheaper call. Nothing in the existing API changed.

- **`tests/run_memory_test.sh`** (suite `memory`, test `memory_test`): three programs that build and drop the same structure at two iteration counts a hundredfold apart, failing if peak RSS grows by more than 4 MB between them. A leaked reference shows up in nothing else — not in output, not in stack depth, not in a short run — and the three defects fixed below each hid behind a suite that was entirely green. Run it with `./tests/run_all.sh --suite memory`.

- **`stack fn` — a function whose arguments stay on the stack.** Naming a parameter binds it as a local on entry, which is why `fn double(x:i64 -- i64) { 2 * }` failed: `x` had been consumed into the binding, so the body started with nothing on the stack. That behaviour was carried by the presence of a colon, so an annotation that reads as documentation decided what the body meant, and the two forms could not be mixed. The `stack` modifier carries it instead: `stack fn double(i64 -- i64) { 2 * }` leaves the arguments where the caller put them. Under `stack`, parameter names are optional and are documentation only — they appear in `quaddoc`, editor hints and diagnostics, they are not in scope, and the body may bind a local of the same name with `->`. Without `stack`, every input must be named, since there would be nothing to bind; the old *"Cannot mix named and unnamed input parameters"* rejection is gone, replaced by an error that names both fixes, and naming only some inputs of a `stack fn` is allowed because it changes nothing but the documentation. A `stack fn` must take at least one input. Modifiers may be written in any order; `quadfmt` normalises them to `pub inline stack`. The 27 functions in the standard library and examples that used unnamed parameters now carry the modifier and the names their documentation already gave them: `bits::extract(value:i64 start_bit:i64 num_bits:i64 -- result:i64)` had been `extract(i64 i64 i64 -- result:i64)`.

- **`while` is back, and the condition is written once.** `cond while { body }` loops while the condition holds, re-evaluating it at the head of every iteration, so the body does not restate it and a condition that is false to begin with runs the body no times. The `while` removed earlier was `cond while { body … cond }` — it popped a flag and the body had to leave the next one, which is the same line count as the `loop { cond if { break } … }` it was replaced by, so it saved nothing. The condition is the shortest run of words before the keyword whose net stack effect is `( -- flag )`: the parser takes the preceding expression run and the validator trims it to that suffix, so a neutral statement before the loop — `"starting" print nl` — is evaluated once rather than drawn in and repeated. A run leaving two values, or none, is a compile error naming what was left, and the body must leave the stack as it found it. `break` and `continue` work in it as in `loop`.

- **`strings::byte_len`**, the size of a string's UTF-8 encoding. `strings::len` counts characters now, so the byte size needed a name of its own for sizing a buffer or writing to something that counts octets; it was otherwise reachable only through the raw pointer from `strings::data`. It replaces `strings::char_count`, which counted codepoints and so became an exact synonym for `len` (it had no uses outside its own tests).

- **`math::inf`, `math::nan`, `math::is_nan`, `math::is_inf`, `math::is_finite`.** Infinity and NaN have no literal spelling, so before this a program could only obtain one by dividing and could not test for one at all -- NaN is unequal to itself, so `x x ==` was the only NaN check and it reads as a mistake. The usual seeds (`+infinity` for "smallest so far", NaN for "no result yet") are now writable.

- **`print` renders arrays.** `[1 2 3] print` printed an empty line — `qd_print` had no pointer case and fell through. Arrays now print by element type (`[1 2 3]`, `[1.5 2.5]`, `[a bb]`, `[]`) and nest (`[[1 2] [1 2]]`), to a depth limit of 8, beyond which the remainder prints as `…` so a self-referential structure cannot run off the stack. `printv` gets the same rendering. Structs print as `<struct 0x…>`: the runtime knows a pointer is a registered struct but not its layout, so field-by-field output stays `fmt`'s job, where the types are known.

- **Exhaustiveness warning for a `switch` over an enum.** When every arm names a variant of one enum, there is no `_` arm, and some variant is unnamed, the compiler now says which: *"switch on enum 'Color' does not handle Blue; add the missing arm(s), or a '_' arm if that is deliberate"*. A missing variant was previously caught only by accident, when the function's declared outputs happened to expose it. It is a **warning, not an error**, on purpose: an enum variant is an `i64` and nothing tracks that the value being switched on came from that enum, so the check reads the author's intent off the case labels rather than off a type, and inferred intent should not be fatal. Arms drawn from two different enums, or mixed with literals, are not judged. `-Werror` promotes it like any other warning.

- **`sort::by`, `sort::is_sorted_by` and `sort::lower_bound_by`**: sorting, checking and binary search ordered by a caller-supplied comparator, using the same negative/zero/positive convention as C's `qsort`. The module's six entry points each fixed both the element type and the direction because a function could not take a comparator; sorting by a key, by several fields, or descending are all just comparators now.
- **Function-pointer tests**: `fntype/fn_field_dispatch` (dispatch through a struct field, plus fields returning several values, none, and a struct that is chained), `fntype/fn_param_call` (a declared parameter, through a type alias and passed on to another function), and the rejections `compile_errors/fn_field_signature_mismatch` and `fn_call_result_unconsumed`.
- **Generics tests**: `generics/generic_array_param` (`[]T` bound to i64/str/f64 element types), `generics/generic_fn_param` (`fn(T -- T)` with a named fn, a differently-typed one, and a lambda), `generics/generic_struct_return` (fields of a returned `Box<T>`), `modules/module_generic_arrays` (the same through module-qualified calls), and the rejections `compile_errors/generic_binding_conflict`, `generic_fn_param_mismatch`, `modules/module_array_param_mismatch`.
- **`switch` arm stack-effect rule** (spec §6.4.1). Every arm that reaches the merge point must leave the stack at the same depth, as `if`/`else` arms already had to; a `switch` with no `_` arm must additionally leave the stack as it found it, since no arm may run. `c switch { 1 { 10 }  2 { 20 30 }  _ { 0 } }` in a `( -- r:i64)` function used to compile and return whichever value happened to be on top. Diverging arms are exempt, and after a bare fallible call the `Ok` arm is seeded from the call's results and every other arm from the pre-call stack.
- **`qd_stack_truncate(ctx, target)`** in `libqdrt`, and a matching freestanding stub. Emitted on the failure exit of every fallible function: see the runtime entry under *Changed*.
- Regression tests pinning the checks that were switched off (below) with a call in the body — `compile_errors/arity_check_after_call`, `arity_check_after_module_call`, `if_arms_unbalanced_after_call`, `defer_effect_after_call` — plus `failure_arm_drop`, `fallible_if_result_unconsumed`, `switch_arms_unbalanced`, `switch_no_default_changes_stack`, and positive tests for balanced-arm retyping, fallible methods before `if`, fallible `if` without `else`, `Ok` versus a literal `1` arm, `panic` followed by dead code, and module functions with no outputs and control flow in the body.

- **fish completions** (`completions/quad.fish`), covering all ten tools with per-option descriptions, subcommand dispatch for `quad` and `quadpm`, and passthrough so `quad lint --<TAB>` offers what `quadlint` accepts. File operands are filtered to `.qd` (and `--css` to `.css`) rather than merely ranked: `__fish_complete_suffix` sorts matches first but still returns every file, so it would have offered `CHANGELOG.md` for `quadfmt`. fish autoloads by command name as bash-completion does, so `make install` links `<tool>.fish` for each tool alongside `vendor_completions.d/quad.fish`; the file is staged into `dist/` and shipped in the release tarball. `cli_surface_test` checks the tool list and the option lists against each tool's `--help`, and runs `fish -n` where fish is available.
- **zsh completions** (`completions/_quad`), covering all ten tools with per-option descriptions, `.qd`-filtered file arguments, and subcommand dispatch for `quad` and `quadpm` — including passthrough, so `quad lint --no-<TAB>` offers what `quadlint` accepts. One file serves every tool: its `#compdef` line names all ten and zsh indexes it by them, so unlike bash-completion it needs no per-command links. Installed to `$DATADIR/zsh/site-functions/_quad`, staged into `dist/` and shipped in the release tarball. `cli_surface_test` checks the `#compdef` line, the `$service` dispatch and the option lists against each tool's `--help`, and syntax-checks the file with `zsh -n` where zsh is available.
- **`quaddoc` reports files it could not parse**, as `file:line:column: warning: ...`, the located form `quadc` and `quadlint` use, and carries on documenting what did parse. A file the parser chokes on used to be published silently with whatever the text scanner happened to recognise. `-q` silences it.
- **`qdcli::Help`** (`lib/cli/src/help.cc`): a shared renderer for the tools' `--help` pages. Each tool describes its own options and examples; the title line, `Usage:` block, section headings and column alignment are computed in one place. The ten pages had been hand-written `std::cout` sequences with five different description columns between them.
- **`tests/run_cli_surface_test.sh`** (suite `tools`, test `cli_surface_test`): 277 checks pinning what all ten tools share — the shape of `--help`, the format of `--version`, how an unrecognised option is reported, and that the bash completions still list every option each tool documents. Run it with `./tests/run_all.sh --suite tools`.
- **`completions/quad.bash` rewritten** against the tools' actual flags, and covered by `cli_surface_test`, which now fails if an option in any tool's `--help` is not completable. It had drifted a long way: no `--no-color` anywhere, no `quadmcp` at all (despite its own header claiming it), no `pm` or `mcp` under `quad`, no `remove`/`outdated` for `quadpm`, and `quadlint` was missing ten of its flags including `--json`.
- **Long forms for `quadc`'s short options**: `--output`, `--debug`, `--stack-size`, `--include` and `--module` alongside `-o`, `-g`, `-s`, `-I` and `-l`, and `--output` for `quaddoc`'s `-o`. The short spellings are unchanged; every option now has both, as the other tools' already did.
- **`--no-color` on `quad` and `quadmcp`**, the last two tools that rejected it. `quad` consumes it and exports `NO_COLOR` to the tool it runs, so `quad --no-color lint src/` reaches `quadlint`.
- **`BaseOptions::optionError`**: lets a tool's option handler report what was actually wrong with a flag instead of `parseArgs` falling back to "unknown option", which blamed the flag rather than its missing value.
- **`SemanticValidator::finalStackTypes()`, `finalStackStructTypes()` and `finalStackFunction()`**: what the most recently type-checked function body leaves on the stack, including the struct type of each pointer. A REPL compiling one line at a time needs this to re-declare the previous line's end state as the next line's signature.
- **`quadrepl` `:doc <name>`**: shows a name's stack effect — builtins and keywords from the compiler's own reference table, standard library functions from their declaration in the installed `.qd` sources, and functions defined earlier in the session. With no exact match it lists every name containing the text, so `:doc trim` finds `strings::trim_left` without knowing the name.
- **`quadrepl` command aliases**: `:quit` and `:exit` alongside `exit`/`quit`/`:q`, and `:save`/`:load` alongside `.save`/`.load`.

### Changed

- **Twenty-one functions are written in the stack-direct dialect, and the rest deliberately are not.** `stack fn` made the second dialect first-class but almost nothing used it — 27 of 452 functions that take parameters — and `hof`, a Factor-shaped combinator library, was at zero. Every combinator was written both ways before choosing, and the answer is a rule: a body whose parameters are used once, in the order the caller pushed them, is re-pushing what the caller already arranged. `hof::apply` was `x f call` and is now the single word `call`; `when` and `unless` become one line each, and the stack form says what the bound one hid — `swap 0 != if { call } else { drop }` shows that the function is discarded when the condition fails. A body that uses a value twice or takes two functions goes the other way: `bi` stack-direct is `pick rot call rot rot call` and `both` is `dup rot swap call rot rot call swap`; both were written, both pass, and neither tells a reader anything, so `bi`, `tri`, `keep`, `dip`, `both`, `bi_star`, `times` and the array combinators keep their names. The same rule converted eighteen pure pass-through wrappers whose body was exactly the word being wrapped — the fourteen `sys` port/load/store wrappers, `mem::free`, `path::parent`, `thread::sleep`, `regex::unwrap_re` — and left the 41 other mechanically-convertible bodies alone, because `time::add` as `+` and `term::up` as `"\x1b[%dA" fmt::sprintf` lose the one place the argument order was visible. Call sites are unaffected either way: this is a body-only change, and `hof`'s 22 tests and the stdlib's 959 pass unchanged.

- **A sized integer type is rejected where it has no width to describe.** `i8`…`u64` describe a width *in memory*: they are what a `packed struct` over a binary format is made of, and what the `mem` accessors select. Everywhere else the value is a 64-bit stack slot, and the annotation was accepted and silently did nothing — `300 cast<u8>` yielded `300`, not `44`; `fn f(x:u8 -- r:u8)` promised a byte and got an `i64`; `var count:u32 = 1000` stored a `u32` in name only, as its own test admitted in a comment. The specification had already answered this ("valid as struct field types and as the width selector on raw memory accessors") and carried a note recording that the implementation diverged; the implementation now agrees with it, and the note is gone. The four positions — parameter, return value, module-level `var`, `cast` target — report which two places a width means something and suggest masking (`value 255 and`) for the truncation `cast<u8>` looked like it offered. Struct fields, packed structs and the `mem` accessors are untouched. Nothing in the corpus used one: 0 signatures, 0 casts, and one test whose whole subject was the inert case.

- **`printsv` is removed.** Recounted over `stdlib`, `examples`, `tests` and `cmd`: it has no uses anywhere, in tests or out, while `prints` has 38 and `printv` 5. Both of those stay — the debugging affordance is the point of them — and what goes is the form that is their cross-product and that nobody has ever written. Writing it reports the removal and points at `prints`, as the removed shufflers do. `free` and `dec`, which the review also proposed cutting, were never removable: `mem::free` is implemented with `free`, and `dec` is the same instruction as `--`, which has 37 real uses.

- **`pick` copies the third value and no longer takes an index; `roll` is gone.** Both took their depth from a value popped at run time, which no static stack model can follow: the compiler could not say what a body containing one leaves, and code generation rejected them outright in the functions it evaluates on a compile-time stack — a word that works everywhere except where the optimiser looks is not one word. `pick` is now `( x y z -- x y z x )`, the fixed-depth word Factor keeps, checked like `over` and lowered onto the compile-time stack like the other shufflers. `roll` is not a word any more; it remains as the internal op that brings a method's receiver to the top, and writing it reports the removal with the rewrite (`-> c -> b -> a  b c a`), as the other removed shufflers do. Corpus cost: `pick` had no uses at all and `roll` had two, both in one test.

- **`strings::char_at` is total: an index outside the string is `strings::NotAChar` (-1), not an error.** Scanners are its whole readership, and every one of them reads "the character here, if there is one" — json's, uri's and path's loops each bounds-check before every call. Because it was fallible and those scanners are not, all 67 call sites in the standard library had to spell it `char_at!`, so a single missing bounds check aborted the host process: `json::get_int` on the malformed document `{"a":1,` killed it outright, as did `json::array_len` on `[1,` and `json::get_bool` on `{"a":`. -1 is not a codepoint, so it compares equal to no character a scanner tests for and the loop ends on its own; it is the sentinel convention `strings::index_of` already uses, and the totality `strings::slice` has always had as `substring`'s non-aborting counterpart. Call sites lose the `!` (or `?`) and nothing else — no public signature in any module changed. Use `strings::len` where "past the end" has to be told from a character the string really holds.

- **`unicode` is now actually Unicode, and keeps its name.** It was a table of ASCII character codes whose `to_upper` was `c a - A +` — correct for ASCII, a silent no-op above it. Once `strings` became properly UTF-8 the two layers disagreed about the same character: `"é" strings::is_alpha` was true while `unicode::is_alpha` of that codepoint was false, and `strings::upper` produced `É` where `unicode::to_upper` returned `é` unchanged. The eleven functions that were bounded by that arithmetic (`is_upper`, `is_lower`, `is_alpha`, `is_alnum`, `is_space`, `is_digit`, `is_print`, `is_control`, `is_punct`, `to_lower`, `to_upper`) now share `strings`' codepoint tables through a new header, so one implementation answers both layers. Existing calls are unchanged: ASCII results are identical and non-ASCII ones are now correct. The two modules are complementary rather than overlapping — `strings::is_alpha` asks about a string, `unicode::is_alpha` about a single codepoint — and the codepoint layer matters more now that `strings::char_at` returns codepoints.
- **`unicode::is_ident_start` and `is_ident_cont` are pinned to ASCII.** They were defined in terms of `is_alpha`/`is_alnum` and would otherwise have followed them into the rest of Unicode; specification §2 restricts identifiers to ASCII letters, digits and underscores. The module's character-code constants, `is_hex_digit`, `is_ascii`, `digit_value`, `hex_digit_value` and the UTF-8 mechanics helpers stay as they were — they are ASCII notation or byte arithmetic by definition.

- **`str` is genuinely UTF-8, and its unit is the codepoint.** The specification has always called `str` an "Immutable UTF-8 string" while every operation in `strings` worked on bytes. `strings::len` of `"héllo wörld"` was 13 rather than 11, `char_at 1` returned 195 -- the first byte of the é, not a character the string contains -- `index_of` reported byte offsets, and `upper` left exactly the letters that needed it alone. Every index and length in the module now counts characters, and `char_at`/`from_char` carry Unicode codepoints. The type was the one described in the spec; the library was not.
- **No string operation can produce invalid UTF-8 any more.** `strings::reverse` reversed *bytes*, so `"héllo wörld"` came back as mojibake with every multi-byte character shredded; `substring`, `slice`, `insert`, `remove_range` and `truncate` could cut inside a sequence and leave a truncated character (`"héllo" 0 2 substring` produced the bytes `h 0xC3`); `from_char` truncated any codepoint above 127 to a single byte; and the padding functions emitted `pad_ch[0]`, the first byte of the pad character on its own. All of these now work on whole characters.
- **Case mapping covers the cased scripts, not just ASCII.** `upper`, `lower`, `capitalize`, `title`, `equals_ignore_case`, `is_lowercase` and `is_uppercase` map per codepoint across Latin-1, Latin Extended-A and Additional, Greek and Cyrillic, computed from the structure of those blocks rather than from a shipped copy of UnicodeData. So `"héllo wörld" upper` is `HÉLLO WÖRLD`, `"Привет" upper` is `ПРИВЕТ`, and `"ÄPPLE" "äpple" equals_ignore_case` is true. Mappings that change length (U+00DF sharp s to "SS") and locale-dependent ones (Turkish dotless i) are deliberately not applied: a one-to-one API cannot express them, and turning one character into two would invalidate every index the caller holds. Scripts without case are returned unchanged, which is the correct mapping rather than a gap.
- **`is_alpha`, `is_alphanumeric` and the trim family are per codepoint.** `"héllo" is_alpha` and `"日本語" is_alpha` were both false. `trim`, `trim_left`, `trim_right`, `is_blank`, `title` and `words` now treat the Unicode spaces -- a pasted non-breaking space included -- as whitespace.

- **`cast<T>` no longer converts a string to a number; that direction is a compile error.** Every other conversion `cast` offers is total -- int to float, float to int, anything to string -- so its result never needs checking. Parsing is not total, and `cast` reported failure as the value `0`: `"notanumber" cast<i64>` and `"0" cast<i64>` gave the same answer with nothing to tell them apart, and `"42abc"` silently became `42`. `strconv` already had the fallible version of each (`atoi`, `parse_int`, `parse_float`, `parse_bool`), so this was a quiet duplicate of an existing API rather than a feature; making `cast` fallible instead would have cost every total conversion a failure arm. The error names the replacement. The same refusal is in the interpreter tier, which can be exact about it because the operand's type is on the stack. One program used it -- `examples/dc/dc.qd`, which guarded with its own `is_number` first and now calls `strconv::parse_float!`. The learn and reference pages were teaching the unsafe form, including two examples that read a line from the user and cast it straight to a number; they now use `strconv` and show the failure arm. Specification §3.7 states the totality rule.

- **Float division by zero follows IEEE 754 instead of aborting.** `1.0 0.0 /` is `inf`, `-1.0 0.0 /` is `-inf`, and `0.0 0.0 /` is NaN. The integer rule -- fatal at run time, a compile error for a literal `0` -- had been applied to floats as well, in the validator's literal check and again in the runtime's `qd_div`. The language already contradicted itself about this: the compiled path emits a bare `fdiv`, so `fn d(a:f64 b:f64 -- r:f64) { a b / }` called with `1.0 0.0` returned `inf` while `0.0 -> z  1.0 z /` killed the process with *"Fatal error in div: Division by zero"*. Integer division and modulo by zero are unchanged, and `mod`/`%` remains integer-only (`math::fmod` is the float remainder). Specification §12.1 gains a **Float semantics** paragraph.
- **Array literal elements may be any single-value expression.** Codegen emitted only `LITERAL` elements and skipped the rest without a word, so `7 -> x  [x 2 3]` compiled to the two-element array `[2 3]`. A literal whose elements are not all scalar literals is now built through the stack -- the array is created with no element type and each element appends itself -- which also gives struct literals (`[ P { x = 1 } P { x = 2 } ]`) and any nesting depth for free. All-literal arrays keep the existing constant path.
- **The element type of an array literal is inferred from all of its elements**, not just from element zero and only when that was a scalar literal. `fn mk(x:i64 -- r:[]i64) { [x 2 3] }` was rejected with *"expects type '[]i64' but got '[]any'"*; nested literals now type as `[][]i64` rather than `[]any`. Elements whose types are known and disagree are a compile error; anything undecidable still falls back to `[]any`.

- **Specification §11.2.1, "Reference Cycles"**: reference counting alone must not be expected to reclaim a cycle, an implementation is not required to detect one, and this one provides neither a cycle detector nor weak references — a program that builds cyclic structures must break them itself. Non-cyclic nesting is explicitly unaffected: a chain of pointer-typed fields is reclaimed in full when its head is released. §11 described refcounting for structs, arrays and strings without ever saying what it cannot do, while §3.6.2 uses `struct Node { next:*Node }` as its illustration of pointer fields.

- **`hof` is generic.** All seventeen combinators were fixed to `fn(i64 -- i64)` because a generic function-pointer parameter could not be satisfied; they now carry type parameters, so `apply`, `map`, `fold`, `filter`, `any`, `all` and `find` work over floats, strings and structs. `map` is `map<T, U>`, changing the element type — `["a" "bbb"] &length_of hof::map` yields `[1 3]`. The seventeen existing i64 tests pass unchanged.
- **Arrays decide their element type on first use.** An empty `[]` literal was created as an *int* array, so `[] "x" append` failed at run time with a type mismatch, and a generic `map<T, U>` could not build its result. An array now starts with no element type (`QD_ARRAY_TYPE_ANY`) and adopts the type of the first value appended — or written with `set`, which is how `make<T>` inside a generic function behaves, since generics are erased rather than monomorphised and `make<T>` cannot know T at run time. Reading a slot of an array that never received a value gives the integer zero, which is what the zeroed slot holds. `qd_makea` is the new runtime entry point for that case; `make<i64>`, `make<f64>`, `make<str>` and `make<SomeStruct>` are unchanged.
- **The function-level output check compares pointer types structurally**, with the function's own type parameters as wildcards — inside `fn map<T, U>( … -- r:[]U)` the result is built from an empty literal, which is `[]any`, and U is unbound in the body. It was a string equality over array types only, so it rejected that and skipped struct results entirely; a function declaring `-- p:A` while returning a `B` now reports it.

- **A function pointer can be called through a struct field or a declared parameter.** Nothing converted a `fn(...)` type *string* back into a signature — `mPendingFnSignature`, which `call` consults, was set only by `&f`, a lambda, or a local bound directly from one. Everywhere else `call` took its "we don't know what the called function will do" branch: it popped the pointer and pushed nothing. So `s <<area call print` reported a stack underflow, and a fn-typed parameter was no better; the cases that appeared to work did so only because a leftover argument stood in for the missing result. `parseFnTypeString` is the inverse of `buildFnTypeString`, and `call` now falls back to it using the type the value carries. Dynamic dispatch through a struct field — a vtable — works, including fields whose functions return several values, no values, or a struct that is then chained into a field read.
- **`call` no longer switches off the function-level checks.** Its branch fell out of the `if`/`else if` chain in `typeCheckInstructionInternal` into the trailing `mHasUnpredictableStack = true`, which is a plain statement rather than an `else`, so every function containing a `call` lost its arity, `if`-arm and `defer` checks — the same shape as the `IDENTIFIER` bug fixed above, and the reason `fn run(f:fn( -- f64) -- ) { f call }` compiled while leaving a value behind. The flag is now set only when the callee's effect is genuinely unknown, which is still the case for an untyped `ptr`.
- **A function pointer is checked against the field it initialises.** The struct-construction field check had no case for `&f` or a lambda, so their type was `UNKNOWN` and any function satisfied any `fn`-typed field: `H { f = &shout }` with `f:fn(i64 -- i64)` was accepted. The comparison it does reach was a raw string compare, which would have rejected the `fn(-- f64)` spelling `buildFnTypeString` emits against a declared `fn( -- f64)`; it now unifies structurally, as call arguments do.
- **`buildFnTypeString` renders declared type names**, so a function returning a struct is `fn( -- Point)` rather than `fn( -- ptr)` — the coarse stack types cannot tell those apart, and a field declared `fn( -- Point)` would not have matched. `any` and a bare `ptr` mean "not known well enough to check" only where a comparison starts: nested they are real element types, so an empty `[]` literal (`[]any`) still fails against a declared `[]i64`. A field initializer is strict from the start, since it is a definite assignment rather than a value of unknown provenance — `old_make -> x  Container { data = x }` with `x:ptr` stays an error.

- **Generic type parameters unify structurally, so `[]T` and `fn(T -- T)` work.** Parameter and result types were compared as literal strings by `structTypesMatch`, so `fn count<T>(a:[]T -- n:i64)` rejected `[1 2 3]` with *"expects type '[]T' but got '[]i64'"* and `fn apply<T>(x:T f:fn(T -- T) -- r:T)` rejected `&dbl`. A call site now unifies each declared type against the argument's, recursing through `[]X`, `fn(A -- B)` and `Name<X>` and binding the type parameters as it goes (`unifyTypeName` in `semantic_validator_internal.h`), then substitutes the bindings into the results. `FunctionSignature` carries the declared type names and the function's type parameters, which it previously dropped; the coarse `consumes`/`produces` types cannot express this, since `[]T` and `[]i64` are both `PTR`. This is why `sort` has six monomorphic entry points and `hof` is hardcoded to `fn(i64 -- i64)` — those APIs can now be generic, and `type` aliases for fn-pointer types become usable. An `any` on the argument side means "unknown" only at the top level: nested, it is a real element type, so an empty `[]` literal (typed `[]any`) still fails against a declared `[]i64` while binding a `[]T` freely.
- **A type parameter used twice must bind to one type.** `fn same<T>(a:T b:T -- r:T)` accepted `1 "s"` — there was no binding environment at all, only a "first TYPEVAR wins" heuristic that also mistyped the results of `fn pair<A, B>`. Results are now substituted from the real bindings, so `[1 2 3] first 10 +` type-checks as `i64` and `"a" wrap <<value` as `str`.
- **Module-qualified calls check their argument types.** The struct/array/fn-pointer parameter check existed only in the unqualified-identifier path, so `mod::f` accepted anything of the right coarse type. Both paths now share `bindCallTypeParams` and `pushCallResults`; an unqualified struct name that names an imported module's struct is canonicalised (`Flag` ↔ `flag::Flag`) before comparison, which is how the check passes on code that mixes the two spellings.
- **An instantiated generic struct keeps its type arguments.** `Box<i64> { value = 5 }` pushed the type `Box`, so `<<value` reported the field as the declaration's `T`. The struct-type stack now carries `Box<i64>`, `lookupStructFieldTypes` strips the arguments, and the new `resolveFieldType` maps a field declared as a type parameter to the corresponding argument — so `5 wrap <<value 1 +` type-checks and `>>value` still accepts any type when the instantiation leaves the parameter open.

- **`ident <<field` is no longer folded by the parser.** When the token before `<<` was a plain identifier, the parser deleted that node and stored its name inside the field-access node, and every consumer then had to redo name resolution to learn whether it had been a variable, a function or a struct type. Codegen got all three right; the validator had no function branch and fell through to "search every struct for a field with that name", so a call with arguments before `<<` never consumed them — `7 mk1 <<a` reported one phantom value, `7 8 mk2 <<b` two — and `5 wrap <<value print nl drop` compiled and then underflowed at runtime. The identifier now stays its own node and `<<field` always reads the struct on top of the stack, exactly as `>>field` always did. `AstNodeFieldAccess` and `AstNodeFieldSet` carry only the field name; the JSON AST dump no longer has a `varName` key. Three places that had silently depended on the folded name were made stack-based with it: the validator's construction-time field-initializer evaluator (which had no `<<` case at all, so `Vec2 { x = a <<x ... }` reported the *struct* as the field value once the operand was a real node), the isolated signature analysis (which pushed the field without popping the operand), and closure codegen, which registered captured variables without their struct type. A zero-argument call before `<<` on a field name shared by several structs also resolves now — codegen used to hit its ambiguity fallback because the folded path never consulted the call's return type. The `error <<code`/`error <<message` special case that rode on the fold is gone; its one use, a program embedded in `tests/run_tools_test.sh`, now reads the code with `err` as the documentation says to. `<<` and `>>` diagnostics name the struct and suggest fields; `>>field` additionally checks the value's type against the field's.
- **The declared-effect, `if`-arm and `defer` checks now run in functions that call other functions.** `mHasUnpredictableStack = true` in the validator sat *after* the block that applies a resolved call's signature, so it executed for every `IDENTIFIER` and `SCOPED_IDENTIFIER` call, resolved or not — the comment beside it described the not-found case the code never tested for. The three checks gated on that flag (`declares N output(s) but body leaves M`, the `if`/`else` depth rule, and `defer` must have zero net effect) were therefore dead in any function that called anything, since the check was introduced in `3267700f`. `fn bad( -- r:i64) { helper 99 }` compiled clean. All four regression tests pinning the arity error had literal-only bodies, so the suite could not see it. The flag now moves into the not-found branch of both copies. **This is breaking for code that was wrong**: the sweep over the whole standard library and every example found three functions (below), and the test suite found nine tests encoding pre-spec conventions, all rewritten.
- **A failure arm is modelled from the pre-call stack, and a `drop` in it is a compile error.** The validator seeded the `else` arm of an `if` after a fallible call from the *success* stack ("both branches receive result values from fallible calls"). At runtime the call produced nothing, so `drop  // drop unused string` in `flag::int`/`flag::float`'s failure arms popped the *caller's* value from the shared stack before panicking — verified with a sentinel — and `examples/errors/errors.qd` taught the same pattern. The arm now starts from the stack as it was before the call, so the `drop` underflows at compile time, which is what spec §10.3 has said all along. The `Ok` arm of a `switch` is seeded from the results and every other arm from the pre-call stack; a literal `1` arm is an error-code arm, not `Ok`.
- **The success arm of a fallible `if` must leave the same depth as the failure arm.** Previously any depth mismatch after a fallible call was suppressed wholesale. With the failure arm modelled correctly the general rule applies, so `divide if { "ok" print nl } else { ... }` — which leaves the result on the success path only — is rejected with a hint to consume or drop it. A fallible `if` with no `else` likewise merges to the pre-call stack and requires the success arm to leave that depth (`try_all` in the error-handling docs, which drops the result in each arm, is the shape that now type-checks *because* of this: it used to be reported as leaving four values). The spec's own §10.6 example left the result on two "unreachable" success arms and has been corrected.
- **A fallible function's failure exit truncates the stack to what the caller expects** — the depth at entry minus the declared inputs and receiver. `panic` branched to the return block and left the stack as it was, so a callee with unnamed parameters that panicked before consuming them (`fn g(i64 -- i64)! { dup 0 < if { "neg" 1 panic } ... }`) left its input for the caller's failure arm, and the old "push an error value, then panic" convention in four tests relied on exactly that. Named-parameter callees already behaved correctly because binding pops the inputs at entry. The truncation makes the validator's model exact for every callee body, releases any strings it drops, and leaves pointers alone for the same reason `drop` does.
- **Balanced `if`/`else` arms now yield the arms' types, not the pre-`if` types.** The merge handled effects `> 0` and `< 0` but had no branch for `== 0`, so arms that transformed a value in place (`-> s  s parse_float` in one arm, a diverging `panic` in the other) reported the *input's* type as the function's output: `flag::float ... expects float but got string`.
- **A block diverges when any top-level statement in it is `panic`, `return`, `break` or `continue`** — not only when the last one is. `"msg" 1 panic  0.0` was not recognised as diverging, which is why `flag.qd` carried dummy pushes after its panics. `break` and `continue`, which spec §6.1.1 always listed, were not checked at all.
- **A fallible *method* call before an `if`/`switch` is recognised as one.** The check looked the callee up by bare name; methods are keyed by their mangled name, so `f name string if { ... }` inside `flag.qd` was treated as an ordinary `if`. Both `if` and `switch` now resolve the preceding call through one helper that knows about methods and module qualification.
- **Module functions with no declared outputs produce nothing.** `analyzeModuleFunctionSignatures` fell back to the isolated body analysis' residual stack when a function declared no outputs, and for any body with a loop, `switch`, `if` or an unmodelled call that residual was the function's own *inputs*. `bytes::fill(value buf offset count -- )` was registered as producing four values, `bytes::copy` five, and any `( -- )` module function with a loop leaked its inputs into the caller's model. `collect.cc` had already rejected this idea ("body analysis is unreliable for control flow"); the module builder now agrees, and its scalar type mapping goes through `stringToStackValueType`, so sized-integer parameters in module functions are checked as integers instead of accepted as `any`.
- **Generic type parameters are skipped in method-call argument checks**, as they already were in function-call checks. `v 10 push!` on a `Vec<i64>` reported *"Parameter 1 expects typevar, but got int"* once the signature carried the parameter's real type.
- **Diagnostics** for the `if` rule report the arms' resulting depths (`then: 2 value(s), else: 1 value(s)`) rather than effects measured from different bases, and carry a hint after a fallible call.

- **`quaddoc` reads declarations from the compiler's AST.** It was the only tool that re-implemented parsing, matching `pub fn`, `struct`, `const` and struct fields with 28 hand-written regular expressions, and it silently dropped every form those patterns had not anticipated. Structure -- which declarations exist, their names, parameters, receivers, generics and visibility -- now comes from `Qd::Ast`, the same parser `quadc`, `quadlint`, `quadfmt`, `quaduses` and `quadlsp` use. 12 regular expressions remain and none of them parse Quadrate: ten match the `@param`/`@return`/`@error`/`@example`/`@field` tag language, which lives inside comments the lexer discards and so has no AST, and two expand `use foo.qd` file includes before parsing.
- **Parameter tables describe the parameters the function actually has.** Names, types and order come from the signature; `@param` and `@return` supply only the prose, matched by name and falling back to position. Where the two disagreed the documentation used to publish the tag: `bits::set_bits` was documented as taking `target value start_bit num_bits` when it takes `tgt val sb nb`, and every `rand` receiver was typed `ptr` where the declaration says `Rng`. A method's receiver is now the first row of its parameter table rather than being dropped.
- **Every tool's `--help` follows one layout**: `<tool> - <summary>`, a description paragraph, `Usage:`, an `Options:` block opening with `-h`/`-v`/`--no-color` in that order and worded identically, any tool-specific sections, then `Examples:`. `quadlsp`, `quadmcp` and `quadrepl` had no examples; `quadfmt` listed the stdin note in the middle of its options; `quaddoc` and `quadmcp` folded their description into the title line. `quad`'s page no longer colours itself, matching the other nine, and its command list is generated from the dispatch table it already had rather than retyped beside it.
- **Compiler diagnostics drop the `quadc: ` prefix** when they carry a source location: `main.qd:7:2: error: ...` rather than `quadc: main.qd:7:2: error: ...`. This is the gcc/clang form every editor's error parser expects, it is what `quadlint` already emitted, and the prefix is wrong on its face in a reporter that `quadlsp` and `quadrepl` link too — both were announcing themselves as `quadc`. `quadc`'s own failures (`quadc: no input files`) keep the prefix, since nothing else identifies them. The error-limit note no longer names a tool either. 28 `.err` test patterns updated.
- **`quadpm`'s diagnostics match the other tools.** It printed a capitalised, red `Error: `/`Warning: ` prefix where every other tool writes `<tool>: <message>` in lower case on stderr; 23 sites now go through `pmError`/`pmWarn`/`pmUsageError`. Scripts grepping for the old `Error: ` prefix need updating — the text after `quadpm: ` is otherwise unchanged in meaning.
- **`quadmcp --version`** reports `quadmcp <version> (<commit>, built <date>)` like its siblings instead of a bare `quadmcp 0.5.0`. It is compiled from `.qd` and cannot include the generated `version.h`, so the Makefile emits the same string as a Quadrate `const` from the same two `git describe` calls meson and `lib/version` use.
- **`quadlint` reports a bad option value once.** `--max-nesting` with no argument printed `quadlint: --max-nesting requires an argument` followed by `quadlint: unknown option: --max-nesting` — two lines contradicting each other. It now prints one, in the `option '--max-nesting' requires an argument` wording the other tools use.
- **`quadc` with no arguments** reports `quadc: no input files` on stderr and exits 1, rather than printing its whole help page to stdout with a failure status. The tools that take paths all behave this way now; `quad` and `quadpm` dispatch commands, so a bare invocation of those still shows help and exits 0.
- **`quadrepl` keeps values on the stack.** A line that left values behind did not compile — `repl_main` declared no outputs — so the REPL retried it with a synthetic `print nl drop...` until an arity fit, printing the values and then dropping them. Every prompt therefore showed an empty stack, which is most of what a stack language REPL is for. It now asks the validator how many values the body leaves and declares that many `any` outputs, so `5 3` gives `[5 3]>` and `add` gives `[8]>`. Values are no longer echoed a line at a time; with stdin on a pipe the final stack is printed at end of input, as `-p` does explicitly.
- **`quadrepl` tab completion reads the standard library from disk.** The hand-maintained table it replaces offered `strings::index`, `strings::substr`, `strings::ltrim` and `strings::rtrim` — the real names are `index_of`, `substring`, `trim_left` and `trim_right` — spelled the math constants `PI`/`E`/`TAU` instead of `Pi`/`E`/`Tau`, and knew nothing of the modules added since it was written.
- **`quadrepl` compiles and runs each line once.** Every line used to be compiled and executed with the whole session replayed in front of it. That made a session quadratic, and it re-ran side effects: one `io::append_file` followed by three more lines wrote four lines to the file. A line is now compiled on its own, taking the state the previous line left — the stack, and the names bound at top level — as its input signature and handing it back as outputs. The arity probe that cost up to eight codegen-and-link cycles per line is gone with it; the count comes from one in-process validation pass.
- **`quadrepl` accepts `struct`, `enum`, `const`, `type` and `var` declarations.** Only `fn` and `use` were recognised, so `struct Point { x:i64 y:i64 }` went into the body of the generated function and came back as `Undefined identifier 'struct'`. Declarations are kept for the rest of the session, as function definitions already were.
- **u8t tokenizer updated to 1.4.0.** The local `u8t-scanner-eof.patch` is dropped — upstream now stops a string token at end-of-input without consuming the terminator, which is what the patch did. Malformed numeric literals (`0x`, `0b` and `1e` with no digits after them) are reported as `Unexpected character` rather than `Invalid integer literal`; the tokenizer classifies them as errors instead of handing the text to the parser. Rejection of exponent notation is unchanged: `1e300` is still an error, `2.2250738585072014e-308` is still a float.

### Fixed

- **A thread's stack is as big as the context that spawned it.** Both spawn paths created the thread's context with a hardcoded 1,024 elements, so a thread body that pushed more died with *"Stack overflow (use -s to increase stack size)"* — advice that could not work, because `-s` sets the main context's size and nothing carried it across. The thread now inherits the spawning context's capacity, and the fallback that was a bare `1024` in three places is `QD_DEFAULT_STACK_SIZE`. A thread that pushes 3,000 values now runs under `-s 8192` and still overflows at the default, which is the answer the message always implied.

- **An anonymous function follows a named function's rules.** They had drifted apart in seven places. A bare type name in a lambda's parameter list was read as a parameter *name* with no type, so `fn (Str -- ) { drop }` bound a local called `Str` and started the body on an empty stack — the branch that did it contradicted its own comment, which said "identifier is the type, not a name", and a named function's parameter list had always read it that way. Unnamed inputs were accepted and silently left on the stack, where a named function rejects them and tells you to name one or write `stack fn`; a lambda had no way to spell `stack fn`, so the stack form was reachable only by accident. Parameter and output type names were not validated, so `fn (x:Nope -- r:i64)` compiled. Unused parameters were not reported. Fallibility was inherited from the enclosing function, so a `panic` inside a plain lambda inside a fallible function passed validation and was then compiled by a generator that hard-coded the lambda as non-fallible. Outputs were compared by primitive type only, so a lambda returning the wrong struct type went unnoticed. And `fn (...)!` did not parse at all.

  A lambda now takes `stack` and `!`, wherever one may appear — a statement, a struct literal's field, an array literal's element. Binding is decided by `stack` in the parser, the validator and the generator alike; each of the three used to apply its own "only when every parameter is named" heuristic, agreeing with the others by coincidence rather than by rule. A fallible lambda's call site behaves like a call to a fallible name: `call!` aborts, `call?` propagates, and a bare `call` must be read by `if` or `switch`, which now see the status and the results the way they do after a call by name.

  That last part fixed a bug with nothing to do with lambdas: **`call!` never checked for an error**, so `&risky call!` on a pointer to a fallible named function ran straight on past a panic and the next instruction underflowed on the value the callee never pushed. The indirect call site now clears the error state before the call and reads it after, like every other fallible call site.

  The 65 lambdas in the corpus that relied on unnamed parameters say `stack fn` now. One limit remains, and it is the same for named functions: an `fn(...)` type string has nowhere to write `!`, so a fallible lambda stored in a struct field or passed as a plain `ptr` arrives at the call site looking infallible.

- **An anonymous function's body is stack-checked.** Nothing checked it: the case in the validator's block walk pushed a function pointer and moved on, under a comment saying code generation would validate the body, which it does not. `5 fn (x:i64 -- r:i64) { 2 * } call` compiled and died at run time with *"Fatal error in mul: Stack underflow"*, where the identical body in a named function is a compile error — naming a parameter binds it, so `2 *` has one operand. The body is now checked the way a named function's body is: on its own empty stack, with named parameters bound (only when every one of them is named, the rule code generation already applies — otherwise the arguments stay on the stack) and captured variables typed from the scope the lambda was written in. It reports what a named function reports, plus *"Anonymous function declares N output(s) but body leaves M value(s) on the stack"* and an output-type mismatch. All three places a lambda can appear are covered: a statement, a struct literal's field initializer, an array literal's element.

  Turning it on found three more `hof` examples with the same mistake the earlier docs pass had missed (`fn (x:i64 -- r:i64) { dup * }`), two callbacks in `os_test.qd` that never consumed the argument their unnamed parameter left on the stack, and two C++ fixtures that asserted zero errors for bodies that underflow — `AnonymousFunctionSimple` and `AnonymousFunctionCapture` were written `{ dup mul }` and `{ base add }`. Seven tests now pin the check, including the two shapes that used to pass.

- **The `-> result` annotation in an `@example` no longer swallows the line.** `gen_docs.sh` matched the arrow greedily and turned everything after the last one into a comment, so an example that binds a value in the middle of a line lost the rest of it: `io::readline`'s example rendered as `io::readline switch { Ok { -> ok  // line ...` and could not parse. The annotation is recognised only when what follows the last arrow is a list of names or literals, which is what an annotation is; anything else is code and stays code. Fixing it exposed twenty-seven examples whose tails had been hidden inside that comment, in `path`, `hex` and `fuzzy` — all now compiled.

- **`hof`'s examples pass their argument to the function they demonstrate.** Seventeen were written `fn (x:i64 -- r:i64) { 2 * }`, which underflows: naming `x` binds it, so the body has one operand. They read `{ x 2 * }` now. The compiler does not catch this in an anonymous function — see the TODO entry — so the examples compiled and would have failed for anyone who ran one.

- **The math module's examples show the arguments in the order the language takes them.** Every method example was written argument-first — `other v subtract`, `normal v reflect`, `point m transform_point` — where the call convention is receiver-first, so each one computed the wrong thing or did not compile. Fifty examples are rewritten and now run: `v3 other3 subtract` is the difference the page says it is. The page declares the values they are written against with `doccheck: page-setup`, so the examples stay one line long and are compiled on every docs check.

- **A doc comment can contain a `|` again.** `gen_docs.sh` packs each function into a `|`-separated record, so `math::abs`, which documents its return as `|x|`, split into extra fields: the page lost the return description, grew a phantom error table with a `math::x` row, and rendered its example as `||-5.0 math::abs print`. The records use an ASCII unit separator now, which a doc comment cannot contain, and a `|` reaching a table cell is escaped.

- **The front-page example compiles.** `fn double(x:i64 -- result:i64) { 2 * }` in `about.md` has been wrong since the page was written: naming `x` binds it, consuming it off the stack, so the body underflowed. It reads `x 2 *` now, with a sentence on what naming a parameter does and the `stack fn` form shown beside it. `docscheck` skips any block without a `fn main`, which is why a year of readers met a broken example first — see the R9 entry in TODO.md for what it would take to close that gap, measured.

- **Two pointers compare by identity instead of killing the process.** `==` and `!=` accepted two numbers, two strings, or a pointer against an integer — the null check — and two pointers were a fatal *"Type error (expected numeric or string types for comparison)"*. Structs are references, so that is also the only way to ask whether two struct values are the same struct: "is this child the last one", the question every walk over a linked structure ends on, could not be written, and `json::put` asks `c <<next null ==` instead. Both operands are released either way, as the earlier fix in this release made them. Ordering is unchanged and still numeric: `<` on two addresses is a type error rather than an address comparison, since the relative order of two allocations is not something a program should be written against. Specification 12.2 now states the operand rules for `==`/`!=` — by value, by content, by identity — which it never did.

- **A generic method's result takes the type its receiver's type arguments give it.** `Box<i64> unwrap`, calling `fn (b:Box<T>) unwrap<T>( -- v:T)`, pushed the bare type parameter, so `b unwrap 2 *` failed with *"Expected numeric types, got typevar and int"*. Everything a generic container gave back was in the same position: usable only where `any` is accepted, which is why nothing in the corpus ever passed a `Vec<T>` to a function of its own. The binding machinery already existed for plain calls — all four method-call paths went around it and pushed the declared types unsubstituted. They now bind the struct's type parameters from the receiver's type arguments, so `v 0 get!` on a `Vec<i64>` is an `i64`, on a `Vec<f64>` a float, and on a `Vec<str>` a string that `strings::concat` will take.

- **Naming a type from a module that is not imported says so.** `fn f(b:sb::StringBuilder -- )` without `use sb` reported *"Invalid type 'sb::StringBuilder'. Valid types are: i64, f64, str, ptr, any, or a struct name"*, which reads as though another module's struct cannot be named in a signature. It can, and always could. The message now names the qualifier: *"module 'sb' not imported. Add 'use sb' to name its types"*, or *"module 'sb' has no type named 'Nope'"* when the module is imported but the type is not there.

- **`ct::Vec`, `ct::Queue`, `ct::Deque` and `ct::Map` hold any element type, not just `i64`.** `push` and `get` went through `mem::set_i64` and `mem::get_i64` whatever `T` was, so `Vec<f64>` and `Vec<str>` stored an element and read back `0`, and `Vec<SomeStruct>` segfaulted on `get`. Every test in the module instantiated `i64`, which is why a container library that worked for one type read as working. Elements now live in tagged slots (`mem::set_any`), so a container reads back what was put in, and it holds a reference to a string or a struct until the element is popped, replaced, reset away or released with the container. An element is 16 bytes rather than `sizeof<T>`: one body has to hold every `T`. `Set` is unchanged — its keys were always strings.

- **`Pair<T, U>` can be constructed.** `Pair<i64, str> { first = 5 second = "x" }` was rejected with *"Field 'second' expects ct::U, but got string"*: a module struct's field types are qualified with the module name so that `ControlPoint` in `spline` matches `spline::ControlPoint`, and the struct's own type parameters went through the same path — `U` became `ct::U`, which is not a type parameter of anything. The same declaration written in the program rather than a module always worked. Type parameters are now left unqualified.

- **A map key is copied by bytes.** `ct::Map` and `ct::Set` sized the key copy with `strings::len`, which counts codepoints, so a key with any non-ASCII character in it was stored truncated: `"héllo"` and `"héll"` were the same key.

- **A value read out of a `*T` field knows it is a `T`.** `*T` names a struct as surely as `T` does, but the field's type was recorded as a bare pointer with the name thrown away, so `node <<next -> c  c total add_to` resolved `add_to` against nothing: to a builtin of that name, which reported *"Type error in 'add': Expected numeric types, got ptr and ptr"*, or — when the method's name was not also a builtin — to nothing at all, emitting no call and no diagnostic. That is what silently swallowed every element of an array in `json::stringify` until the call sites were written `c as Value b write`. The field's declared type now reaches both the validator and codegen, so the method resolves, a chained `<<` resolves, and the six `as Value` annotations in `stdlib/json` are gone. `as` still works and still means the same thing. A field declared `*T` also keeps accepting `null`, which is how every linked structure starts (specification 3.6.2); one declared `T` does not.

- **`cast<T>` rejects a target it does not convert to.** Anything the type parameter did not match fell through to a STRING default in silence, so `p cast<Node>` type-checked and produced a string, and the mistake surfaced far away as *"the value on the stack is string, not a struct"*. A misspelling did the same: `42 cast<i65>` was a string. Both are errors now, and the struct case points at the remedy — *"use 'value as Node' to read a pointer as a struct"* — since `as` is a compile-time annotation where a cast implies a conversion. `cast<T>` inside a generic, where the target is a type parameter, is unaffected.

- **`sb::append` copies bytes, `sb::append_char` writes UTF-8.** `append` sized its copy with `strings::len`, which counts codepoints, so appending `"héllo"` copied five of its six bytes and the result was cut inside a character: `"héll"`. `append_char` wrote the low byte of the codepoint and called that a character, so anything above 127 produced a lone lead or continuation byte — not the character, and not valid UTF-8 either. `append` now uses `strings::byte_len`, `append_char` encodes one to four bytes and grows the buffer to fit, and `sb::len` is documented as the byte count it always was.

- **`quadfmt` no longer drives a space through `!=` and `==`.** A `switch` arm labelled with a constant reads exactly like a struct construction — an uppercase name, a brace, and an `=` inside — so an arm long enough to be wrapped was expanded as if it were a field list and re-emitted as `field = value`, turning `0 != if` into `0 ! = if`, which does not compile. `make format` could therefore break a working file while `make fmtcheck` passed on the result. The field-initializer scan now tells a lone `=` from the one inside `==`, `!=`, `<=` and `>=`; a real construction with a comparison in a field value, `Flag { on = 3 4 == label = "eq" }`, still expands correctly.

- **A struct stored in a field is freed when the field stops pointing at it.** `>>field` wrote the new pointer over the old one and said nothing to the old value, but a `str`, `ptr` or struct field owns a reference: the push that put the value on the stack took one, and the destructor gives one back. Every overwrite therefore lost a reference for good. A list that keeps a tail pointer leaked every node the tail moved past — and with the node, everything the node pointed at — so `json::parse` leaked two of the four structs in `[1,1]`, and 400 parses of a 200-element document grew RSS by 100 MB. `>>field` now reads the old value, stores the new one, and releases the old, in that order, so storing a value over itself nets out to no change. Both release calls are safe on null, on a pointer that is not refcounted, and on the zero a fresh struct body carries.

- **`==` and `!=` give back the references they were handed.** The string path released both operands; the pointer path — `node null ==`, the test at the head of every walk over a linked structure — released neither, so each comparison leaked a reference and kept the node alive for the rest of the program. Both operands are now released whatever their types. Measured on a loop that parses `[1,1]`: 80,000 structs allocated and 40,000 freed before, 80,000 freed after.

- **A function that calls one taking or returning something other than `i64` is no longer compiled as integer-only.** The integer fast paths store a local without a retain and rebind it without a release, which is sound only when the local can hold nothing but a number. The body scan that selects them rejects string and float literals, struct construction and field access, but a call to a user function is an `Identifier` node and fell through — so `mkx -> tv` in an otherwise-plain `main` skipped the release on every iteration (200,000 structs allocated, one freed) and would have pushed the local back typed as an integer. Every function's signature is now collected before any body is generated, and a caller that names one whose signature is not made of `i64` alone takes the checked paths. Integer code is unaffected: `fib 30` and `tak` compile and run as before.

- **A script's own function is no longer shadowed by a used module's function of the same name.** The embedding API mapped symbols to bare function names by cutting at the second underscore, so `usr_hello_parse` and `usr_json_parse` both landed under `"parse"` and whichever `nm` printed last won — `hello::parse` called `json::parse` and died with a stack underflow. The module's own symbols now take the key; a used module's fills one only if nothing else claims it.

- **A local declared in a loop body gets one binding per iteration.** Its capture block was allocated once in the function's entry block, so every iteration's closure captured a pointer to the same block and closures outliving the loop all read the last value written — three closures built over `i 10 * -> val` printed `20 20 20`. The block is now allocated where the declaration runs, with the previous one released first, so it survives only for whatever captured it and a loop no longer accumulates blocks. The pointer slot starts null, so a declaration in a branch that is never taken leaves nothing to release, and release is one helper shared by the declaration site and function-exit cleanup, which null-checks and releases the element's string or pointer contents before freeing. Capture by reference is unchanged within a binding: reassigning a variable is still visible through a closure that captured it — a new iteration produces a new binding, not a new value in the old one.

- **A closure can capture a `for` iterator, and captures it by value.** `0 3 1 for i { fn ( -- r:i64) { i } … }` reported *"Undefined identifier 'i'"*: the validator tracks a `for` iterator separately from ordinary locals and passed only the locals as the outer scope when detecting captures. Fixing that alone would have produced a wild read, because the generator builds a closure environment out of pointers to each captured variable's slot and an iterator has none — it is an SSA value, replaced each iteration, with no address whose contents could be shared. Each closure is therefore given a refcounted block of its own holding the iterator as it stood when the closure was built, released by the existing closure-release path. A closure created in one iteration and called after the loop reports that iteration's value. By-reference capture would have no distinct meaning for an iterator: assigning to its name inside the body declares a shadowing local rather than moving the loop on. An ordinary *local* declared in a loop body still occupies one slot for the whole loop, so escaping closures over it share the last value — the learn page claimed otherwise and now documents both behaviours, and specification 9.x/11.6 state them.

- **An anonymous function can appear wherever a value can — a struct-literal field, an array-literal element, a nested literal of either.** `H { f = fn (x:i64 -- r:i64) { x 2 * } }` was rejected with *"Use '=' instead of ':' for struct field initializers. Expected 'x = value'"* — the field parser was reading the lambda's own parameter list as another field written with a colon, so the advice was about a field the author never wrote. `[fn (x:i64 -- r:i64) { x 2 * }]` reported *"Unexpected character '('"*. `parseSimpleToken` now recognises `fn (`, which the array-literal loop already routes through, and the struct-literal field parser checks for it before its colon test. Captures work inline, the field is still type-checked against its declared signature, and binding the lambda to a local first — what the corpus does — is unchanged. Specification 8.2 states the general rule: a field initializer is an ordinary expression, and an implementation must accept there anything it accepts as a value elsewhere.

- **`!` and `?` now fire for `mem`, `net` and `http::run`, which they did not at all.** A fallible native function reports failure through the context's error state — that is what `!` and `?` read — while a pushed status is what `switch` reads. `mem_heap.c` (12 failure paths), `net.c` (33) and `http_server.c` (5) set only the status, so the two disagreed: `switch` saw the failure, `!` saw success, fell through, and popped the status as if it were the call's result. The next binding then reported *"Stack underflow when assigning to local variable"*, blaming a binding for an allocation or a connection that failed earlier, and `err` gave code `0` with an empty message. `net` was worse again — every one of its failure paths also returned success to the caller. All three now set the code and a message, push the status and return it, as `io`, `os` and `thread` already did: `mem::alloc!` on a failed allocation aborts with *"alloc failed: mem::alloc: out of memory"*, and a handled failure reads `mem::ErrAlloc` with that message. Specification 10.5 states the rule for native fallible functions, and 11.1 states the standard library's allocation-failure policy — its own allocation sites abort, because a library function has no way to report the failure that would not make every caller fallible for a condition none of them can act on. This is deliberately not how malformed *input* is treated, which a library must not abort on.

- **`strings::substring` returns the error it declares instead of aborting.** It is marked fallible and documents `@error ErrOutOfBounds`, but the implementation called `abort()` on a negative index or a start past the end — so the `switch` every caller wraps it in was dead code, the process being gone before any arm could run. A length that runs past the end is still truncated to what is there, which is now written down rather than left to be discovered.

- **`json` no longer aborts or hangs on a malformed document.** Fuzzing the module's entry points over 8,070 malformed inputs found 10 of the 18 scanned ones killing the process and one looping forever. The aborts were all one shape — a scanner reading the character after a comma without re-checking that the document had not ended — and are fixed by `strings::char_at` being total (above) plus `find_key`, `array_len` and `find_elem` rounding the loop after a comma instead of falling through, so the end of the document and the closing bracket are re-tested at the top where those checks already are. `[1,` also no longer counts the element it does not have. The hang was `json::array_len "[}"`: `type_at` reports `Number` for anything it does not recognise, so a stray `}` left `skip_value` exactly where it started and the caller looped on it forever — `skip_value` now always advances. The same fall-through walked past the `]` of `[,]3` into whatever followed the array. Over 612 well-formed documents every entry point returns byte-identical results to before; over the malformed corpus 48 inputs went from crash-or-hang to clean and none the other way.

- **`drop` releases what it discards.** A stack slot owns one reference to a refcounted value; that was true for strings and not for pointers, so `drop` leaked every array and struct it discarded — 128,000 bytes over a thousand iterations for an array where binding it instead was zero. The same gap was in `clear`, `nip` and the fallible-failure stack truncation. Pointers now follow the rule strings already followed: a push takes a reference of its own, so a value in two slots is counted twice, and a discard drops one. That ordering is what makes `dup` safe — releasing on `drop` without retaining on copy would free a value the other slot still holds. Reference cycles are unaffected and still leak their own nodes, as specification §11.2.1 says.

- **An assertion that fails inside a helper now fails its test.** Assertions report failure by returning a non-zero exec result, and the code generated for a `test` block can only check the calls it emits itself — one frame deeper the value had nowhere to go, so the failure printed its message and a full stack trace and the test still passed. That covered `testing`'s own `assert_gt`, `assert_lt`, `assert_ge`, `assert_le`, `assert_in_range`, `assert_gt_f`, `assert_lt_f`, `assert_positive`, `assert_negative`, `assert_zero` and `assert_nonzero`, which are Quadrate functions wrapping the C `assert_true`: 103 assertion calls across the corpus were inert. The runtime now counts assertion failures on the context, where the depth of the call does not matter, and a test's result folds that in.

- **Character indexing is no longer O(n) per access.** Making `str` UTF-8 meant finding character *i* required walking from the start, so every loop reading a string one character at a time became quadratic: scanning a 20,000-character string took 2.9 seconds, and `json::get_array` over a 60 KB file never finished. `qd_string_t` now memoises its codepoint count — which also identifies the all-one-byte case, where an index is already an offset — and keeps a scan cursor so a forward scan resumes from the last lookup instead of restarting. The cursor's character index and byte offset live in one atomic word, since strings are shared between threads and two separate fields could be read from different updates. Every character-index conversion in the module goes through those memos — including `insert`, `remove_range`, `truncate`, the padding functions and `last_index_of`, which a first pass had left counting for themselves — so no hand-rolled conversion remains. On identical work over 30,000 non-ASCII characters a non-ASCII string now costs 32 ms against ASCII's 27 ms, where it previously fell off a cliff; the 20,000-character scan is back to 26 ms, and `strings::byte_len` remains the O(1) byte size.

- **Calling a module's imported function by its bare name is now a compile error instead of silently wrong code**, including inside the module that declares the import — which is the case that was wrong, since a module's own bodies are not type-checked when a program imports it. A function declared in a module's `import` block does not resolve from an unqualified call, including inside the module that declares the import -- but nothing said so. The call compiled clean and left an extra value on the stack, so a following `if` consumed that rather than the result and always took the true branch: inside `unicode.qd`, `c is_digit if { ... }` made `unicode::digit_value` answer `17` for `'A'` instead of `-1`. The diagnostic names the module and the qualified spelling. It went unnoticed because every module in the corpus already writes the qualified form -- `math::log` is `x math::ln base math::ln /` -- so the convention the code follows happens to avoid it and nothing tested the other shape.

- **Nested array literals parse.** `[[1 2] [3 4]]`, documented in specification §3.2.2, reported *"Unexpected character '['"*. The array-element loop did have a nested-array branch, but it ran only when `parseSimpleToken` returned null -- and that function reports the diagnostic itself before returning, so the recovery could never be reached without an error already on the floor. A struct literal inside an array failed the same way and then spilled the rest of the literal into the top level as four more errors.
- **`--dump-ast` names eleven node types it was printing as `Unknown`**: `ArrayLiteral`, `ArrayIndex`, `FieldSet`, `LoopStatement`, `ImportStatement`, `GlobalVarDeclaration`, `FunctionPointerReference`, `Comment`, `TestDeclaration`, `AnonymousFunction` and `TypeAliasDeclaration`.

- **`quaddoc` signatures with a function-pointer parameter are no longer truncated** — the fault was in `docs/gen_docs.sh`, not the renderer. It matched a declaration's parameter list with `\(([^)]*)\)`, and `[^)]*` stops at the first `)`, which in `pred:fn(T -- i64)` is the one closing the function pointer. Everything after it was cut and the published signature was left with an unbalanced paren: `hof::all` read `(arr:[]T pred:fn(T -- i64)`. The pattern now allows one level of nesting, which is all a function-pointer parameter can have. Seventeen signatures were affected; all stdlib signatures now balance.
- **`gen_docs.sh` preserves `/// doccheck:` directives**, emitted as an `<!-- doccheck: … -->` comment before the example fence. `signal`'s example loops until Ctrl+C and cannot run under docscheck, so its opt-out was being dropped on every regeneration and had to be restored by hand; the directive now lives in `stdlib/signal/qd/signal/signal.qd` and survives.
- **An array that never received an element leaked its buffer.** `case QD_ARRAY_TYPE_ANY:` in the release path broke without `free(arr->data.p)` — correct that there are no elements to release, but the buffer is allocated at creation regardless. Introduced with the adaptive element type above and caught by valgrind.

- **`sort::ints`, `sort::ints_desc`, `sort::floats` and `sort::floats_desc` returned unsorted data.** Each partition bounded its left scan by `j` rather than by `hi`. The scan could then stop on an element that still sorted before the pivot, and the pivot swap that follows placed the pivot to the left of it. Every reverse-sorted input of even length 18 or more came back unsorted — silently, since nothing checked the result. Found while writing `sort::by`, which mirrors the same partition. The pivot at `hi` is the scan's sentinel, so bounding by `hi` is both correct and sufficient. New tests sort reverse-sorted input at every length from 2 to 60 for `ints`, `floats` and `by`; a separate stress run over ~1,000 sorts (random values, heavy duplicates, reverse-sorted, all-equal; ascending and descending) reports no failures.

- **`flag::int` and `flag::float` corrupted the caller's stack when the flag was missing.** Their failure arms dropped a value the failed `string` call never produced, eating whatever the caller had on the shared stack, then panicked; the dummy `0`/`0.0` after each `panic` was dead code. Found by the re-enabled checks above.
- **`regex::get_cclass` pushed the integer `0` where the signature promised a `ptr`** on the not-found path; it now pushes `null`. Found by the re-enabled output-type check.
- **`examples/errors/errors.qd`** dropped a non-existent error value in both failure arms and pushed a dummy result before `panic`; it now reads the error with `err` and matches the spec.
- **Documentation examples that left values on the stack or read the wrong one**: `reference/generics.md` (three `identity` calls with nothing consuming them), `learn/8-examples/user-input.md` (`io::readline` returns `line ok`; two examples bound only one value and a third cast the `ok` flag instead of the line), and the §10.6 worked example in the specification (results left on "unreachable" success arms). `docscheck` covers 218 blocks and passes.
- Nine language tests encoded the pre-spec convention of pushing an error value before `panic` and dropping it in the failure arm (`errors/always_success`, `conditional_error`, `error_recovery`, `recovery`, `fallible_protocol_unified`), or declared no outputs for a function that returns one (`modules/advanced_ops`), or relied on the checks being off (`modules/bytes_module`, `enums/module_enum`, `imports/*`). All rewritten to what the spec says; expected outputs are unchanged.

- **`quaddoc` and `quadmcp` had no shell completion in practice.** bash-completion loads a completion file lazily, by the name of the command being completed, so the one file serving all ten tools needs a link under each tool's name. `make install` created seven links from a hand-written list that omitted those two, and the `dist/` staging step created none at all, so an unpacked tarball completed only `quad`. All three rules now derive the list from one `COMPLETION_LINKS` variable, and `make print-completion-links` exposes it so the test suite checks the real list instead of a copy.
- **The `sys` module was missing from the documentation entirely** -- all 17 functions and the module page. `quaddoc`'s pattern required `pub fn`, so `pub inline fn`, which is how every function in `sys` is declared, matched nothing.
- **The `ct` container library was missing its functions** -- `vec`, `deque`, `hashmap`, `queue`, `pair` and `set` published a struct and nothing else, and `ct` itself showed 4 of its 22 functions. A generic declaration such as `pub fn (v:Vec<T>) push<T>(elem:T -- v2:Vec<T>)!` did not match a pattern that expected `(` straight after the name.
- **Signatures with a function-pointer parameter were truncated mid-type.** `hof::map` was published as `fn map(arr:[]i64 f:fn(i64 -- i64)` -- the parameter list was cut at the first `)`, losing the rest of the parameters and the entire return section. 17 signatures were affected.
- **Receiver methods were rendered as syntax that does not exist**: `fn f:Flag destroy()` rather than `fn (f:Flag) destroy()`. 105 signatures were affected; they can now be pasted back into a source file.
- **The cross-reference graph counted words in comments, builtins and field accesses as calls.** It matched identifiers in raw body *text*, so `rand::next` was listed as calling `rand::new` because its body says "Return new state" in a comment, `math::abs` as calling the `Vec2` method `math::neg` because it uses the `neg` builtin, and every `sb` function as calling `sb::len` because of `<<len` field accesses. 36 such edges are gone and no genuine call was lost.
- **`ImportedFunction::line` and `::column` were wrong in any file containing non-ASCII before the declaration.** The import parser passed `u8t_scanner_token_start`, a character index, straight to `fastLineColumn`, which wants a byte offset; every other call site converts first. In `math.qd`, whose doc comments give ranges as `[-π/2, π/2]`, the recorded line drifted further out with each multi-byte character, so 22 of the imported functions lost their documentation once `quaddoc` began looking declarations up by line. This also misplaced compiler diagnostics pointing into import blocks.
- **`tests/quadpm/test_quadpm.sh` blocked for a minute and then failed tests 36 and 37** on any machine with `commit.gpgsign` set globally. One of its seven throwaway git repositories did not disable commit and tag signing the way the other six do, so `git commit` waited on pinentry. The suite now finishes in under a second instead of timing out.
- **`quadmcp` ignored an unrecognised option and started serving anyway**, exiting 0. A mistyped flag therefore looked like a hang to whoever typed it, since the process sat waiting for JSON-RPC on stdin. It now reports the option and exits 1 like every other tool.
- **`quadpm` printed its entire help page to stdout on an unknown command**, burying the one line that said what was wrong. It prints the two-line diagnostic on stderr instead.
- **`echo 'code' | quadc` could not reach the stdin path.** `quadc` short-circuited on `argc == 1` before argument parsing, so the "no files and stdin is piped" branch was unreachable without a flag; `quadc -r` worked and bare `quadc` did not.
- **`quaddoc -o`, `--title` and `--css` with no value** were reported as unknown options rather than as options missing an argument.
- **`use` of any standard library module failed from a build tree.** `qd_build` looked for module archives under `lib/<name>/` and module sources under `lib/qd<name>/qd/<name>/`; both moved to `stdlib/<name>/` in 0.5.0 and these two lookups were not updated. Nothing was linked, and the module failed at `dlopen` with an undefined `usr_<module>_<function>`. This made the whole standard library unusable in `quadrepl` and in any host embedding `libqd`.
- **`quadrepl` rewrote the word `print` inside string literals.** The print-to-`print nl` conversion and its inverse for history matched substrings, so `"hello print world"` evaluated as `"hello print nl world"`. Both now skip string literals and comments.
- **`quadrepl` prompt escape sequences** are wrapped in `RL_PROMPT_START_IGNORE`/`RL_PROMPT_END_IGNORE`, so readline no longer counts the colour codes as visible columns and misplaces the cursor on a wrapped line.
- **`quadrepl` `reset`** left the runtime stack in place while clearing the history behind it.
- **`quadrepl` history file** grew without bound; it is now capped at 5000 entries.
- Stack floats print as `2` and `1.41421` rather than `2.000000`; long strings are elided in the prompt but shown whole by `stack`.
- `qd_clone_context` leaked `error_context` when the `program_name` copy failed.

### Removed

- **The `error { code = … message = … }` literal.** It was specified as the alternative to `msg code panic` and had four uses in the tree, three of them its own tests. It was never a value: the parser rewrote it into a struct construction under the reserved name `__error__`, and the validator and generator each carried a special case that pushed the message and code for `panic` to consume — so it was `msg code panic` with braces, kept alive by three special cases across two tiers. Using it now reports *"the 'error { … }' literal has been removed; use 'msg code panic' instead"*, as a single error: a removed `name { … }` construct used to also produce a bogus *"Unmatched '}' at top level"*, because error recovery stopped at the opening brace and left the closing one to be read as the enclosing block's.


- **`ctx` keyword**: `ctx { ... }` ran its body on a copy of the stack and appended only the body's top value to the parent. Nothing in the corpus used it and the static checker could not model it. There is no drop-in replacement — inlining the body is *not* equivalent, since it consumes the values `ctx` preserved; bind what the body needs with named locals and push the result explicitly. Using it reports the removal.
- **Eight stack shufflers**: `drop2`, `dupd`, `nipd`, `over2`, `overd`, `swap2`, `swapd`, `tuck`. All had zero uses; named parameters and `->` locals cover what they did. Using one reports the removal together with its old stack effect and the equivalent named-local rewrite.
- **Eight C runtime entry points** (`qd_drop2`, `qd_dupd`, `qd_nipd`, `qd_over2`, `qd_overd`, `qd_swap2`, `qd_swapd`, `qd_tuck`) from `<quadrate/rt/runtime.h>` and `libqdrt`. **This is a breaking change for out-of-tree embedders** that called them directly: `libqdrt.so` carries no soversion, so the upgrade is silent and fails at link or load time with an undefined symbol. Replace each call with the equivalent sequence of `qd_stack_push`/`qd_stack_pop`.
- Phantom `error` builtin from the language reference. It was documented with a signature and an example but never existed; the instruction is `err`.

## [0.5.0] - 2026-04-16

### Added

- **`inline` function modifier**: functions declared with `pub inline fn` are inlined at every call site via LLVM's `AlwaysInline` attribute. Works at all optimization levels including `-O0`.
- **`sys` standard library module**: zero-overhead inline wrappers for raw memory access (`sys::st8`/`st16`/`st32`/`st64`, `sys::ld8`/`ld16`/`ld32`/`ld64`), x86 I/O ports (`sys::port_in8`/`port_in16`/`port_in32`, `sys::port_out8`/`port_out16`/`port_out32`), and CPU control (`sys::cli`, `sys::sti`, `sys::hlt`).
- **Freestanding compilation** (`quadc --freestanding`): compile without libc for bare-metal targets. Emits `.o` with a `_start` shim using a static runtime context. Rejects hosted-only builtins and most stdlib modules at compile time.
- **Freestanding runtime** (`lib/rt/src/freestanding.c`): minimal no-libc runtime with static context, halt hooks (x86/ARM/AArch64), and value-stack operations. No heap, no I/O.
- **Freestanding-safe `mem` module**: split into `mem.c` (safe subset: `set_byte`, `get_byte`, `copy`, `zero`, `fill`) and `mem_heap.c` (heap-using: `alloc`, `realloc`, `free`). Freestanding builds link only the safe subset.
- **Raw memory builtins** (`__st8`/`__st16`/`__st32`/`__st64`, `__ld8`/`__ld16`/`__ld32`/`__ld64`): zero-overhead store/load lowering directly to LLVM instructions. Internal — use `sys::st8`/`sys::ld8` instead.
- **x86 I/O port builtins** (`__port_in8`/`__port_in16`/`__port_in32`, `__port_out8`/`__port_out16`/`__port_out32`): lower to inline assembly. x86/x86_64 targets only.
- **CPU control builtins** (`__cli`, `__sti`, `__hlt`): lower to single inline assembly instructions.
- **Type alias declarations** (`type` / `pub type`): compile-time type aliases resolved during semantic validation.
- **String interpolation** (`$"hello {name}"`): desugars to `sb::new`/`sb::append`/`sb::finish`.
- **Boolean literal type**: `true`, `false`, `Ok`, `Err` parsed as boolean literals.
- **Build cache**: content-based incremental compilation using FNV-1a hashing. Skips codegen when output is up-to-date.
- **Test coverage** (`quadc --coverage`): function-entry instrumentation with coverage report after test runs.
- **`quaddoc` cross-references**: call graph with `calls`/`calledBy` arrays and hyperlinks.
- **`quadlint` `//nolint` directive**: per-line or per-rule lint suppression.
- **Typed C embedding API**: `qd_pop_i()`, `qd_pop_f()`, `qd_pop_s()`, `qd_pop_p()`, `qd_error_code()`, `qd_error_message()`, `qd_clear_error()`, `qd_context_stack_size()`.
- **`quadpm` semver-aware update**: resolves constraints from `qd.json`, checks git tags, installs newest compatible version.
- **Improved semver conflict detection**: `rangesHaveCommonVersion()` probing across caret/tilde/explicit ranges.
- **`quadmcp` dynamic module list**: loaded from `docs/api/modules.json` instead of hardcoded.
- **Array syntax in signatures**: `[]i64`, `[]f64`, `[]str`, `[]ptr` types.
- **Function pointer syntax in signatures**: `fn(i64 -- i64)` types in struct fields and parameters.
- **Automated AUR package publishing** via SourceHut CI.
- **`cast<i64>`** now supports pointer-to-integer conversion via `uintptr_t`.
- **Bare-metal x86_64 kernel example** (`examples/kernel/`) with GDT, IDT, PIC remapping, PIT timer interrupts, PS/2 keyboard driver, VGA text output, screen scrolling, backspace, and a `> ` shell prompt. Written in pure Quadrate with assembly bootstrap.
- **New examples**: `csvcut`, `mandelbrot`, `brainfuck`.
- **New test suites**: build cache, freestanding compilation, raw memory, type aliases, string interpolation, inline functions (10 test cases).
- **Documentation**: `inline` keyword in specification, keyword reference, quick reference, and function tutorial. AUR installation instructions.

### Changed

- **`quadfmt` rewritten**: AST-based formatting replacing line-based approach. Formatter now preserves the `inline` keyword.
- **Version numbering** derived from git tags instead of a static `VERSION` file.
- **Deduplicated compiler errors**: parsing errors deduplicated by `line:column:message`.
- **Method call resolution**: uses `userFunctions` map instead of mangled name construction, fixing collisions with builtin instruction names.
- **LSP signature formatting**: empty parameter lists no longer produce spurious ` -- `.
- **Benchmarks modernized**: named parameters and operator syntax replacing stack manipulation.
- **CI**: `quadfmt --check` added to Arch, Alpine, and Debian builds.
- `AlwaysInlinerPass` now runs at all optimization levels (including `-O0`).
- `GlobalDCEPass` skipped in freestanding mode to preserve `pub` functions callable from assembly.
- Target triple and data layout set early in code generation for correct struct layouts on cross-compilation targets.
- Stack struct fields `capacity` and `size` changed from `size_t` to `uint64_t` for consistent layout across 32-bit and 64-bit targets.
- Freestanding mode: `pub` functions get external linkage so they survive DCE and can be called from assembly.
- `make format` now formats both C++/H files (via `clang-format`) and `.qd` stdlib/example files (via `quadfmt -w`).

### Fixed

- `<` operator code generation edge case.
- `cast<i64>` on pointer values no longer crashes with "Cannot cast type to integer".
- Compile-time stack path for `st8`/`ld8` family: fixed a latent bug where these builtins would read from the wrong stack in native functions.
- Formatter output validation distinguishes source parse errors from formatter bugs.
- i386 data layout patched with `i64:32:64` to match the System V ABI alignment.

### Removed

- `lineWidth` formatting option from `quadfmt`.
- `pkg/deploy-aur.sh` deploy script (replaced by CI-based AUR publishing).
